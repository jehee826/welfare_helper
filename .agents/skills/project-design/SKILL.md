# 설계·협업 계획

최신 업데이트: 2026-11-04 15:45 KST

1. 루트 AGENTS.md, 기존 협업 계획의 해당 태스크와 관련 현행 설계만 읽는다. 요청·현재 동작·미구현·미확정을 구분하며 계획 검토를 구현/배포로 바꾸지 않는다.
2. 사용자 흐름→API/저장 계약→담당 파일→선행 작업→실패 동작→완료 기준을 구체화한다. 담당자별 독립 clone·전용 브랜치·허용 변경 경로·기준 main을 기록하고, 같은 파일은 단일 작성자로 배정한다. 같은 checkout/브랜치 공동 개발이나 worktree를 해결책으로 쓰지 않는다. 설계 세션은 제품 코드를 읽되 직접 구현/실행 시험하지 않는다.
3. RAG는 직접 사용자 발화·공식 원문, 화면 안내는 공개 DOM·기존 LLM·실제 요소 강조를 기준으로 한다. 저장 프로필 전송, 이미지, 자동 클릭, 새로운 판정 엔진을 임의로 추가하지 않는다. 문서별/예시문구별 특례로 품질을 맞추지 않는다.
4. 계획은 docs/plan/collaboration-plan.md의 기존 태스크에 계획·실행·검증·테스트로 적는다. 현재 코드 계약이 실제 바뀐 뒤 docs/design의 관련 절을 갱신한다. 설계와 미구현 계획을 섞지 않는다.
   개발 인계에는 3절의 실제 clone/브랜치/정책 버전, 4절의 수정 허용 파일·현재 진입 함수·구현 순서·하위호환·최소 검사·완료물, 5절의 공유 계약을 포함한다. 미확정 제품값과 필요한 운영 승인은 해당 부분의 시작 조건으로 명시하고 이미 결정된 일을 다시 설계하게 만들지 않는다. 계획 사본은 개발자가 동시에 수정하지 않는다.
5. docs/README.md 트리·기존 문서 우선·작성일/최신 시각·실패 이력 보존을 따른다. 설명/결과 MD를 새로 쪼개지 않는다. 원시 자료만 docs/tests에 격리하며 정답표는 적재/모델 입력에서 제외한다.
6. 하위 작업 완료·중요 변경 때 지정된 기록 작성자가 계획과 기존 개발일지를 즉시 갱신한다. handoff는 환경/복구 보조 메모다. 개발 결과·diff·실제 검사 근거를 검토한 뒤 설계 채팅에서 보고한다.
7. 자체 확인·사용자 확인·대역·실제 모델/HTTP/UI/DB를 구분한다. 실패/미확인을 숨기지 않으며 통과한 전체 시험 반복이나 근거 없는 정확도 보장을 계획에 넣지 않는다. 독립 파일 작업은 병행할 수 있지만 의존 API는 서버 PR→클라이언트 PR 순으로 main에 통합하고, 실제 운영 시험은 담당·시간·버전을 하나로 고정한다. 지침의 금지와 Git 서버의 기술적 차단을 구분한다.
