# RAG 정확도 설계

갱신: 2026-11-02. 현재 구현·대역 검증·실제 품질을 구분한다. 실행 경로는 [파이프라인](welfare-rag-pipeline-design.md)을 따른다.

## 0. 설계 요약

정확한 원문 → 구조·위치 보존 청크 → dense+BM25/RRF 검색 → 리랭커 → 근거 기반 생성 순으로 확인한다. 정부기관 자료의 조건·예외·기준일을 보존하고, 자료에 없는 금액·자격·절차는 만들어내지 않는다. 모델 크기나 유사도 점수만으로 답변 정확도를 보장하지 않는다.

## 1. 청크와 오버랩

[split_ranges](../../../BackEnd/rag/chunking.py)의 현재 기본값:

| 항목 | 기준 |
|---|---|
| 본문 목표·최대 | 목표600자, 최대800자 |
| 임베딩 입력 한도 | 헤더+본문을 실제 tokenizer로 계산해 최대400토큰 |
| 오버랩 | 앞 청크의 마지막 완결 문장1개, 80자 이하·40토큰 이하 |
| 적용 조건 | 문장 종결·원문 범위·합친 입력 한도를 모두 충족할 때만 적용 |

글자 수와 토큰 수는 다르다. 모든 청크가600자이거나 항상80자를 겹치는 것은 아니다. 문장·절·표 경계를 고려하고 원문의 char span, source block, 페이지, heading, 입력 해시를 보존한다. 긴 문장·표·헤더가 한도를 넘는 경우를 별도로 확인한다. 수동 검토 단계를 복원하지 않는다.

## 2. 검색과 리랭커

[설정 기본값](../../../BackEnd/core/settings.py)은 dense30개, keyword30개, RRF 이후 최대40개, 핵심 근거6개다. 실제 런타임 환경변수는 이 값을 덮어쓸 수 있다.

bge-m3/1024와 가중치 digest가 맞는 벡터만 비교한다. 한국어 BM25와 dense를 RRF로 합치고 `onnx-community/bge-reranker-v2-m3-ONNX`로 재정렬한다. 리랭커 입력512토큰은 DB 청크 글자 수와 다르다. 점수는 관련성 판단 보조이며 사실 정확도나 자격 확률이 아니다.

현재 [문서 질의](../../../BackEnd/documents/qa.py)는 재정렬 상위 근거에 같은 문서/버전의 관련 부모·조건/예외·질문별 급여/신청 절을 보완한다. 설정에 MIN_DENSE_SIM/MIN_RERANK_SCORE가 존재한다는 이유로 점수 하한 기반 보류가 적용된다고 가정하지 않는다. 현재 문서 QA는 해당 점수 하한을 적용하지 않으며 포함할 원문과 입력 예산을 별도로 확인한다.

문서 BM25는 현재 스냅샷 검증 후에만 서비스별 인덱스1개를 재사용한다. stamp·문서 scope·공개/관리자 범위·임베딩 모델/digest·분석기 identity가 바뀌면 재구축하고, 새 인덱스는 요청 마지막 스냅샷/digest·취소 확인을 통과한 뒤 보관한다. 최대2000청크·인덱싱 입력2,000,000자까지 보관하며 초과 자료도 전량 색인하되 상주시키지 않는다. 이 문자 수는 Python heap 바이트 상한이 아니다. 질문/조건/요약/답변과 기존 옛 ChatService 인덱스는 혼용하지 않는다. DB 전체 스냅샷 검증·Python 벡터 유사도 비용은 그대로이며 실제 규모 성능은 별도 측정이 필요하다.

## 3. 생성과 현재 한계

현재 [복지 정책](../../../BackEnd/documents/welfare.py)은 answer/clarify/no_evidence/out_of_scope 구조와 실제 원문 reference/quote를 검증한다. 인용은 포함 원문 안의 발췌여야 하고 답변의 숫자·전화/URL 표현은 인용 원문과 대응해야 한다. 근거부족·조건 모호성·범위외·검증 실패는 보류/확인 경로를 사용한다. 이는 모든 문장의 의미, 정책 현행성이나 최종 지원 자격을 증명하는 검사가 아니다.

- 실제 원문이 검색됐는지와 생성 답변이 그 원문에 맞는지를 별도로 채점한다.
- 검색 evidence가 반환돼도 문장별 사실 검증이 완료된 것은 아니다.
- 현재 조건·최근 대화·제한된 요약으로 최대1회 맥락을 준비하고 해소된 의도와 이번 원문으로 최대1회 답변을 생성한다. 과거 assistant 답변/요약 전문은 최종 사실 입력에서 제외한다. 전달·요약 갱신 성공을 의미 정확도로 보지 않는다.
- 문서·화면 모두 공통 기한/연결 취소/gate를 사용한다. 동기 native 작업을 떠나기 전 gate를 유지하며 GPU 추론의 즉시 중단을 보장하지 않는다.
- 원문 갱신 중 스냅샷과 digest 일관성을 유지한다.

실제3서비스·67청크/1024 게시 뒤 Qwen1.5B 고정16문항에서 서비스9건 유효 답변0, out_of_scope13·입력예산3이었다. 후속 요약의 잘못된 지원 가능 주장도 확인됐다. 이후 원문 선택/ID 비용 보완은 모델0회 검사로만 확인했으며 실제 품질 재평가는 하지 않았다. 과거 가상 MD 소수 문항 성공으로 이 실패를 대체하지 않는다.

## 4. 평가 순서

먼저 원문 내용·조건·예외와 정답표를 고정한다. 정답표를 검색 자료나 프롬프트에 넣지 않는다. 다음으로 추출/청크 범위, 검색 순위, 리랭크 선택, 실제 답변을 순서대로 확인한다.

질문은 직접 사실, 동의어 표현, 조건·예외, 문서에 없는 정보, 여러 문서가 비슷한 질문을 포함한다. 오류는 원문 누락·추출·청크·검색·생성·응답 검증·실행 실패로 분리한다. MD 평가를 PDF OCR 성공으로 보고하지 않는다.

평가 절차는 로컬 `docs/tests/llm-accuracy-evaluation.md`, 시험 조건과 결과는 `docs/tests/results/`에 둔다. 소수 문항의 단발 정답을 일반적인 환각 방지 보장으로 표현하지 않는다.

## 5. 다음 개선

승인 환경에서 현재 모델의 같은 고정 질문·후속/요약 의미를 재평가한다. 별도로 PDF 표·스캔/OCR·여러 유사 문서의 원문과 정답표를 준비한다. 실제 PDF가 없는 케이스는 준비 필요이며 MD/대역 구조 검사로 PDF/OCR 성공을 대신하지 않는다. 새 모델 도입보다 원문·선택/생성 실패 단계와 예산을 먼저 확인한다.
