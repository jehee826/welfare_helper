## 웹과 로그인

[App.tsx](../../FrontEnd/src/App.tsx)는 루트와 `/admin`을 `/admin/documents`로 보낸다. `/admin/documents`와 `/admin/programs`는 AdminGate로 보호하며 일반 사용자 웹 챗봇 경로는 없다. 정적 파일 자체를 비밀로 취급하지 않고, 관리 API에서 인증을 다시 확인한다.

[관리자 세션](../../BackEnd/admin/session.py)은 환경 설정의 공통 비밀번호를 서버에서 검증한다. 비밀번호를 확장이나 정적 웹에 박아 넣지 않는다. 세션은 **8시간·프로세스 메모리 보관**, 상한 **256개**이며 서버 재시작 시 다시 로그인해야 할 수 있다. Supabase Auth 가입은 이 공통 로그인 경로의 필수 단계가 아니다.

관리자 웹의 `VITE_API_BASE_URL`은 빌드 시 결정된다. production에서 빈 값이면 연결 설정 오류를 안내한다. 정적 웹 배포와 EC2 서버 설정 변경은 별개이며, 실제 배포값은 소스 확인만으로 검증할 수 없다.

## 원문 업로드와 게시

관리자는 사전 등록 제도를 선택하고 출처·기관·자료 기준연도·확인된 수정일 등 메타데이터와 PDF/DOCX/UTF-8 Markdown을 업로드한다. 미상 날짜를 임의로 채우지 않는다. `test_only`는 자료 접근 경계로 사용한다.

```text
인증·제도/파일 검사 → 작업 접수(202) → Docling 분석
→ 구조별 청크 → 실제 임베딩 → 게시 준비 → 성공 버전 게시
```

파일 크기·페이지·문자 수 등의 한도는 설정을 따른다. 작업 상태는 queued/parsing/embedding/ready/succeeded와 실패·취소 상태로 구분한다. 예전 수동 섹션 검토·수동 index 승인 절차는 현재 업로드 경로가 아니다.

원문, 분석, 처리 작업, 청크·벡터와 active 참조는 기존 Supabase 계약을 사용한다. 앱 시작 때 테이블을 자동 생성하거나 기존 자료를 초기화하지 않는다. 원문과 정답표는 분리한다.

## 교체와 조회

새 후보를 분석·임베딩하는 동안 기존 게시 자료를 보존하고, 성공한 후보만 게시한다. 동일 문서 교체의 실패·취소와 재시도·작업 경쟁은 기존 게시본 보존 및 참조 일관성이 핵심이다. 삭제는 관련 참조·제약을 지키는 기존 서버 경로를 사용한다.

[문서 API](../../BackEnd/documents/api.py)는 `/api/v1/admin/documents` 아래에서 업로드, 문서·작업 조회, 교체, 취소, 삭제, 재시도, 원문 조회를 제공한다. 문서별 query는 공통 RAG, search는 문서 범위 dense 검색이다. 진단 토큰만으로 관리자 검색 권한을 얻지 못한다.

주요 구현은 [store](../../BackEnd/documents/store.py), [worker](../../BackEnd/documents/worker.py), [analysis](../../BackEnd/documents/analysis.py), [indexing](../../BackEnd/documents/indexing.py)에 있다.

## 운영 확인의 경계

실제 worker 적재·DB 게시 성공과 **Vercel 관리자 화면 → 로그인 → 업로드 → 교체 → 검색**의 전체 확인은 다르다. UI 접수 성공이나 HTTP 202만으로 게시 완료를 판단하지 않는다. 문서 정리에서 배포·DB 쓰기·모델 추론을 실행하지 않았다.

다음 검증에서는 허용된 시험 자료와 기존 자료의 보존 범위를 먼저 정한다. 스키마·Auth 변경, 자료 전체 삭제, 운영 재시작을 단순 업로드 확인에 자동 포함하지 않는다. 남은 작업은 [협업 계획](../plan/collaboration-plan.md)에서 관리한다.
