## 0. 검토 범위와 표기

- 태스크·기능의 필요성은 재논의하지 않는다. 계획만 읽고 바로 착수 가능한지, 단일 작성자·독립 clone·PR 경로가 지켜지는지, 보존·계약·운영 순서·검증이 빠지지 않았는지만 본다.
- 각 단계의 실제 수정·검증·Git 작업 범위는 해당 절의 기록을 따른다. Claude 1차는 리뷰 작성 당시 제품 테스트·commit·push·운영 작업을 하지 않았으며, 이후 공유 커밋과 혼동하지 않는다.
- 근거 표기: **[확인]** 실제 파일/명령으로 확인, **[추정]** 코드 읽기에 근거한 추론, **[미확인]** 이번에 확인하지 못함.
- 해결 상태: `미해결`(계획 보완 필요), `보완제안`(작성자 판단 필요), `해결`(후속 단계에서 반영 확인 시 기록).
- 식별자: `R1-B##` 차단, `R1-P##` 보완 권장, `R1-T##` 태스크 세부.

### 1.3 착수 전 보완 권장

#### R1-P01. 태스크 최소 검사 다수가 CI에 포함되지 않음

- **대상:** 4절 "공통 개발 시작·검증·완료 절차", W00·W03·W04·W05·W07·W08·W09·W10·W11 최소 검사
- **근거 [확인]:** CI의 Node 검사는 `ci.yml`에 9개 파일을 직접 나열한다(protocol, profile_content, conversations_content, conversation_context, continuous_conversation, panel_usability, timeout, remote_screen, remote_connection). `conversations_worker`·`dom`·`input_assist_content`·`profile_offscreen`은 없다. Python은 `scripts/ci_python.py`에 12개 파일을 나열하며 `test_welfare_qa.py`·`test_conversation_context.py`·`test_desktop_dom.py`·`test_desktop_guidance.py`·`test_extension_cors.py`·`test_public_edge_policy.py`는 없다. 신규 예정 `ui_preferences.test.cjs`(W07)·`answer_speech.test.cjs`(W09)·`consultation_summary.test.cjs`(W10)·`test_conversation_summary.py`(W10)의 CI 등록은 W10에만 언급돼 있다.
- **문제·발생 조건:** PR의 CI 통과가 해당 태스크 검사를 포함하지 않아도 "CI 통과"로 오인될 수 있다. 신규 검사 파일은 CI 파일 작성자(Codex)가 등록하지 않으면 계속 실행되지 않는다. 기존 미포함 파일이 의도적으로 빠졌는지(모델·네트워크 의존 등)는 [미확인].
- **최소 보완안:** 4절 공통 절차에 (1) "PR 본문에 CI 포함 여부와 별도 실행한 검사 명령·결과를 구분 기재", (2) "신규 검사 파일은 해당 기능 PR 병합 직후 Codex 통합 담당이 `ci.yml`/`ci_python.py` 등록 PR을 만든다(또는 등록하지 않는 이유를 기록)"를 추가한다. 기존 미포함 파일의 제외 이유는 Codex가 확인해 기록한다.
- **해결 상태:** 미해결

#### R1-P02. 기능 병합 후 설계 문서·계획 갱신 경로가 불명확

- **대상:** 3절 "설계·정책" 단일 작성, project-design 4항(코드 계약이 바뀐 뒤 docs/design 갱신), 3절 "실제 Chrome 적용" 3항
- **근거 [확인]:** docs/design/**·계획·지침은 설계 단일 작성, docs/Co-op에는 문서만, 기능은 PR 병합으로만 main 반영. 그러나 정책 PR 병합 이후 설계 갱신이 어느 브랜치에서 언제 PR되는지는 "다음 docs 전용 브랜치"라는 Chrome 동기화 문맥 외에는 없다.
- **문제·발생 조건:** 기능 PR이 병합될 때마다 docs/design과 계획 7절을 갱신해야 하는데, docs/Co-op을 계속 쓰면 병합된 브랜치를 재사용하게 되고, 새 브랜치 규칙이 없으면 기능 브랜치에 설계 문서가 섞일 위험이 있다.
- **최소 보완안:** 3절에 "정책 PR 병합 후 설계 갱신은 `docs/<주제>` 전용 브랜치를 최신 main에서 만들어 설계 담당만 작성·사용자 PR로 통합한다. 기능 PR은 docs/design·계획을 수정하지 않는다"를 추가한다. 기능 PR과 설계 갱신 PR의 순서(기능 병합 → 설계 반영)도 함께 적는다.
- **해결 상태:** 미해결

#### R1-P05 · 운영 예약·반납 기록 채택

**반영안:** 원본 계획 7절에 자원·담당·예약 구간·실제 시작/종료·서버/확장 SHA·활성 문서 버전·허용 변경/호출 상한·정리 결과를 설계가 기록한다. 예약은 실행 승인을 대신하지 않는다. 담당이 시작을 인계받고 종료를 보고한 뒤 다음 담당에게 넘긴다. 종료 시각 경과만으로 사용 종료를 추정하지 않는다. 문서 한 줄을 분산 잠금 장치처럼 취급하지 않고 설계가 운영 담당 한 곳을 조정한다.

#### R1-P06 · 다른 기기의 삭제 상태로 한정

**[확인]** 이 기기는 시작 시 clean이고 `docs/data/문서모음`의 MD 10개가 추적돼 있으며 파일도 존재한다. 1차의 미커밋 삭제와 `.playwright-mcp/`는 다른 기기의 기록이다.

**반영안:** 원격 커밋에 파일이 있다는 이유만으로 실행 폴더에도 있다고 가정하지 않는다. W02 실행 담당은 자기 입력 파일 목록·바이트 해시·기준 커밋을 대조한다. 다른 기기의 삭제는 해당 소유자가 의도를 확인하며 자동 복원하지 않는다. 이번에 불필요한 제외 규칙이나 복구 작업은 추가하지 않는다.

#### R1-T01 · W00 전송 본문 단언 명확화 채택

**[확인]** 입력 payload에는 profile을 남기고 실제 HTTP body에는 profile 키가 없음을 확인해야 한다. `protocol.documentRequest`는 현재 profile 입력을 수용하되 반환에서 제외한다.

**반영안:** `Object.hasOwn(body,'profile') === false`와 history/context/timeout/HTTPS 유지 검사를 명시한다. 입력을 제거해 실패를 숨기지 않는다. 최근 추가된 내 정보 ON/OFF 기능은 별도 후속 계약이며 현재 OFF/기본 계약의 선행 검사 정정을 대체하지 않는다.

#### R1-T02 · W06 최초 열기·접힌 상태 검사 채택

**[확인]** `content.js`의 `openPanel`도 clamp를 호출한다. resize만 수정하면 최초 열기/다시 열기에서 고정 위치를 잃을 수 있다.

**반영안:** 열기 직후 오른쪽 도킹, 접힌 상태에서 창 축소 후 펼치기, 닫기/재열기, 자유 배치 복원까지 동일한 도킹 상태를 사용한다. 기존 W06 최소 검사에 이 경로만 더하며 실제 F12 확인은 W07/W09와 묶는다.

#### R1-T03 · W07 sender·알림을 구체화해 채택

**[확인]** worker는 공식 페이지의 top frame·tab ID·sender URL과 tab URL 일치를 검사한다. 기존 storage.onChanged에서 revision을 탭 메시지로 통지하는 경로가 있다.

**반영안:** 화면 설정 메시지는 해당 공식 content 경계만 허용하고 옵션 페이지 권한을 새로 열지 않는다. worker가 `gyeote.uiPreferences`만 직렬로 저장하고 revision 통지 후 content가 최신값을 다시 읽는다. 같은/늦은 revision은 무시하며 꾸미기 설정 변경이 상담 요청을 취소하지 않게 한다. 기존 4MiB 검사는 `gyeote.conversations` 상태의 직렬화 크기이며 UI 설정 키를 합산하는 검사가 아니다. 새 설정은 자체 작은 값 범위와 저장 실패 처리로 제한한다.

#### R1-T04 · v2 백업 제안은 수정 채택

**[확인]** 현 저장소는 변경 작업에서 schemaVersion2를 요구한다. v3를 구확장으로 열면 저장 실패가 가능하다. 단, 같은 storage에 v2 전체를 별도 보존하면 현재 상태와 중복 용량이 발생한다. 기존 4MiB는 상담 상태 하나의 크기 검사이므로 이 제한만으로 전체 저장소의 여유를 보장할 수 없다.

**반영안:** 현재의 합성 v1/v2 이관·쓰기 실패 시 원본 보존 시험을 유지하고, 이관 성공 전 원본을 덮지 않는 절차를 설계한다. 런타임 v2 전체 백업 키를 필수 기능으로 곧바로 추가하지 않는다. 별도 백업을 채택하려면 용량 실패·보존 기간·전체 삭제 시 백업 동시 제거·v3 이후 새 문답 보존까지 계약을 먼저 정한다. 옛 백업으로 자동 복원해 신규 문답을 버리는 롤백은 금지한다. 운영 복구는 v3를 보존하는 호환 수정이 우선이며 구버전 재설치를 간단한 복구로 안내하지 않는다.

#### R1-T05 · W10 request_id의 새 HTTP 계약 명시 채택

**[확인]** 현재 ChatRequest에는 request_id가 없고 추가 필드는 거절한다. 내부 requestId와 새 요약 HTTP 필드는 별개의 계약이다. `GyeoteProtocol.id`의 실제 형식은 `^[A-F0-9]{20}$`다.

**반영안:** 새 요약 endpoint에서만 request_id를 해당 20자리 대문자 16진수로 검증하고 응답에 그대로 돌려준다. 메시지 ID의 `:user/:assistant` 접미사 규격과 혼용하지 않는다. 확장은 요청 ID와 로컬 generation/revision/주제 경계를 모두 대조하며 request_id를 인증이나 서버 중복 실행 방지 수단으로 오해하지 않는다. 신규 경로의 gate·rate·body budget 적용을 함께 명시한다.

#### R1-T06 · 요약 중 전송 비활성 선택, 취소 즉시 자원 해제 가정 금지

**[확인]** `core/execution.py`는 진행 중 실행이 있으면 429를 반환하며 native 호출 종료 전까지 gate를 보존한다. 브라우저 취소만으로 GPU 처리가 즉시 끝난다고 보장하지 않는다.

**반영안:** 요약 중에는 새 질문 전송·중복 요약을 비활성화하고 초안은 보존한다. 사용자는 요약 취소가 가능하며 취소 후 늦은 결과는 버린다. 이후 직접 전송이 아직 바쁜 서버의 429를 받으면 안전한 안내와 초안을 유지하고 자동 재시도하지 않는다. 취소 직후 새 요청을 자동 발사하는 제안은 채택하지 않는다. 다른 탭/다른 사용자의 경합도 UI 비활성만으로 막을 수 없으므로 서버 gate는 유지한다.

#### R1-T07 · W11의 현 범위는 확장 새 reason 필드 없이 가능

**[확인]** `protocol.documentReply`는 reason을 버리지만 `content.js`의 fallback 표시는 현재 `곁에 · 안내`이며 본문은 그대로 표시한다. 따라서 범위 밖 고정 문구 표시에 reason 전달이 필수는 아니다. 현재 서버는 out_of_scope라도 생성 결과가 있으면 evidence를 반환할 수 있어 W11 서버 수정 대상이다.

**반영안:** W11은 out_of_scope일 때 지정 본문과 빈 evidence/contacts를 반환한다. 기존 확장 parser·저장·복원에서 해당 본문과 빈 근거가 유지되는지만 집중 확인한다. 현재 요구만으로 별도 확장 상태 필드/분기/PR을 만들지 않는다. 추후 통계 이벤트를 reason 하나로 계산하는 문제는 2.3의 별도 계약이다.

#### R1-T08 · 연락처 출처와 기관 사이트 구분 후 호환 순서 결정

**[확인]** `documentContacts`의 source_url은 HTTPS `.go.kr`만 수용한다. 이는 안내할 기관의 웹사이트 주소가 아니라 연락처를 확인한 출처 URL이다. 공식 복지로/행정기관 문서가 위탁기관 전화번호를 증명하면 그 공식 출처를 유지할 수 있다.

**반영안:** 위탁기관이라는 이유만으로 호스트 허용 범위를 넓히지 않는다. 실제 CSV/원문에서 외부 공식 출처가 필요한 경우에만 검증된 호스트·출처 계약을 정하고 서버 미전송 호환 지원 → 확장 수용 → 서버 전송 활성화 순서로 진행한다. Git 병합과 실제 EC2/확장 적용은 별개이며 구확장에서 조용히 연락처가 사라지는 조합은 배포 완료로 처리하지 않는다. 임의 URL 허용이나 주소를 거짓 공식 출처로 바꾸는 방식은 금지한다.

#### R1-T09 · 실제 직렬화 payload의 양쪽 예산 대조 채택

**[확인]** DOM 후보 60개/4000자 제한은 양쪽에 있다. label·context·screen_context 합계를 고려해야 한다.

**반영안:** Claude가 바꾼 후보 구성으로 실제 생성한 합성 payload를 서버 DTO에도 통과시킨다. 각자의 별도 예제만 통과해 동일 계약이라고 판단하지 않는다. 60개/4000자 경계와 한도 초과 거절을 확인하고 서버 파일은 Codex만 수정한다. 새 필드가 필요하면 R1-B03의 선행 호환 순서를 적용한다.

#### R1-T10 · 입력·DB 자료 버전 고정은 채택, 자료 확대 일괄 후순위는 수정

**반영안:** W01/W02 실행마다 입력 커밋·실제 파일 목록/해시와 DB의 활성 문서 ID/버전·공개 범위를 함께 고정한다. 입력이 같아도 게시본이 다르면 같은 기준선이 아니다. 현재 10개 기준 검증과 추가 서비스 묶음의 적재/평가는 별도 실행으로 기록한다. 사용자가 서비스 대상 확대를 추가했으므로 모든 새 자료를 W02 전체 완료 이후로 일괄 미루지는 않는다. 기존 10개 최소 업로드 흐름 확인 후 승인된 추가 묶음으로 확장하는 순서를 원본 계획에 명시한다. 다른 기기에만 기록된 미확인 커밋은 현재 자료로 간주하지 않는다.

### 2.3 최근 추가 요구사항과 기존 계획의 충돌

최근 추가 요청은 1차 검토의 W00~W12에 아직 반영되지 않았다. 기능을 실행하라는 요청이 아니며, 이번에는 **원본 계획 변경 없이** 아래 차이를 리뷰에 기록한다. W13~W16 명칭은 기존 대화의 임시 배정안이지 이미 확정·구현된 태스크가 아니다.

1. **복지 서비스 확대 → W02/W01 확장.** 기존 노인 MD10개 업로드 확인을 유지하고 추가 자료 묶음별 출처·버전·중복·대상 확대를 설계한다. 기존 시험 질문만으로 일반화를 주장하지 않고 새 서비스 독립 질문·후속·문서 부재를 포함한다. 원자료 작성은 설계, 적재와 서버 처리는 Codex이며 DB 쓰기는 실행 범위 승인이 필요하다.
2. **129 제외 담당 부서 연결 → W03 보완.** 현재 일반 129 fallback을 목표 달성으로 취급하지 않는다. 부서 ID·서비스/지역 대응·전화번호·출처·검토일·자료 버전의 CSV 입력 계약과 합성 대역을 먼저 설계한다. 실제 연결 검증 시점에만 사용자에게 CSV를 요청한다. 미매칭/폐기/중복 담당 부서 처리와 유효 연락처가 없을 때의 동작을 명시한다. 이번에 129 데이터를 삭제하거나 임의 부서 번호를 넣지 않는다.
3. **내 정보 ON/OFF → 임시 W13.** 현재 지침·계획 C0은 저장 프로필을 검색/생성에 보내지 않는다. 최신 요구는 사용자가 내 정보를 LLM에 줄지 선택하는 기능이므로 미래 ON 경로의 제한된 예외가 필요하다. 기본 OFF, 검색에는 미사용·생성에서만 사용은 제안이며 사용자 확정값으로 쓰지 않는다. OFF 상태의 history/요약에 과거 ON 정보가 남는 문제, 대상이 보호자로 바뀐 직접 발화의 우선순위, 변경 중 요청/저장 경계를 설계한다. 정책/서버 DTO를 Codex, 토글·전송·저장을 Claude가 순차 소유한다.
4. **관리자 상담 조회·부서별 통계 → 임시 W14.** 기존 기기 로컬 보관만 하는 구조에서 서버 저장이 추가된다. 전체 상담 원문을 저장할지, 연락처 안내 이벤트와 필요한 상담만 저장할지 아직 합의되지 않았다. 이를 임의로 축소하거나 전부 저장하지 않는다. 보관/삭제·관리자 접근·식별자·중복 집계·실패 처리, 한 답변의 여러 부서 집계 기준을 먼저 확정한다. 횟수는 LLM 문장 정규식에서 뽑기보다 검증된 contacts와 응답 식별자로 집계하는 안을 검토한다. 서버 생성 시점과 실제 사용자 표시 시점 중 무엇을 세는지 구분한다. W03 부서 계약이 선행하며 BackEnd/DB/FrontEnd는 Codex, 확장 전송이 필요할 때만 Claude 후속이다.
5. **기존 비밀번호 인증 후 새 비밀번호 발급 → 임시 W15.** 비밀번호를 잊은 상태의 복구가 아니다. 기존 비밀번호 재입력 인증 → 발급 버튼 → 정한 형식의 새 무작위 비밀번호를 이후 사용한다. 현재 `BackEnd/admin/session.py`는 설정의 공통 비밀번호와 프로세스 메모리의 8시간 세션을 사용하므로 UI에 난수만 표시해서는 변경이 지속되지 않는다. 서버 보관 위치·해시·원자 교체·동시 발급·기존 세션 처리·재시작 후 유지·실패 시 기존 값 보존을 설계한다. 정규식은 형식 확인이며 난수 생성 자체는 안전한 난수 함수를 쓴다. 실제 .env 편집이나 브라우저 보관을 변경 수단으로 쓰지 않는다. 별도의 확정 버튼 추가는 사용자 확정 요구가 아니다.
6. **웹 챗봇 복원 → W12와 연계한 설계.** 현행 W12는 모바일 방안 검토만 하며 공개 웹 복원을 금지하고 있다. 최신 요청은 복원 방안 검토이므로 상담 중심 웹을 후보로 다루되 관리자 영역/인증을 공개하지 않는다. 기존 EC2 HTTPS API·W08 시간 맥락·W13 선택·W14 저장 계약을 재사용할 범위를 정한다. 공개 웹/모바일 구현 경로·배포는 아직 미확정이며 이번에 앱이나 라우트를 만들지 않는다.
