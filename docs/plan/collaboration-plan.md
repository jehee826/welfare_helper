## 3. Codex·Claude 협업 경계

### 기본 원칙과 실제 준비 상태

협업 방식은 **각 담당자의 독립 일반 clone → 전용 기능 브랜치 → 개별 main 대상 PR → 사용자 검토·승인 후 PR 병합**이다. 같은 브랜치 공동 작성, 같은 checkout 병렬 개발, main 직접 commit/push·PR 우회 반영, worktree 생성/사용은 금지한다. 과거 main 승인3회 예외는 폐기했다. 과거 결과 절의 관련 기록은 당시 사실로만 보존한다.

현재 확인한 작업 폴더는 `C:/Users/jehee/vscode-workspace/welfare_helper`, 브랜치는 `docs/Co-op`이다. 이 저장소의 worktree 목록에는 이 checkout만 있다. 다른 일반 clone의 준비 여부는 아직 확인하지 않았다. **독립 개발 폴더·담당 브랜치를 확인하기 전 병렬 구현을 시작하지 않는다.** 이번 검토에서 clone/브랜치·hook·원격 보호 설정은 생성/변경하지 않는다.

### 착수와 PR 흐름

1. 기존 계획의 해당 태스크 실행 절에 **작성자/검토자, clone 절대경로, Git 디렉터리, 전용 브랜치, 기준 origin/main 커밋, 허용 변경 경로, 계약 버전, 최소 검사, 운영 필요 여부**를 적는다. 이 항목이 불명확하면 해당 구현을 시작하지 않고 독립 읽기 검토만 한다.
2. 같은 main 기준에서 Codex/Claude가 서로 다른 원격 ref의 기능 브랜치를 사용한다. 이름 예시는 `codex/fix-<task>`와 `claude/feat-<task>`다. 이미 배정된 독립 기능은 병행할 수 있다. 같은 담당자의 다음 별도 기능은 이전 PR 검토·병합 확인 뒤 새 main에서 시작한다. 기존 docs/Co-op에는 제품 코드를 넣지 않는다.
3. 편집·stage·commit·push 전에 실제 작업 루트/브랜치/status를 대조한다. main·상대 브랜치·detached HEAD·출처 불명 staged 변경이면 해당 쓰기를 중단한다. 잘못된 위치를 자동 checkout/reset/stash로 수습하지 않는다. diff 파일이 허용 경로를 벗어나면 작성 범위를 조율한다.
4. 각자 기능 구현→관련 최소 검사→상대 읽기 리뷰→설계 판정→로컬 커밋까지 수행한다. 상대 clone에 수정하거나 미병합 코드를 복사/cherry-pick하지 않는다. 같은 파일 리뷰는 작성자에게 제안으로 전달한다.
5. **서버 계약 변경은 Codex PR→main 병합→Claude 기능 브랜치에 최신 main 반영→확장 연결/호환 검사→Claude PR** 순서다. 병합 전 Claude는 합의된 DTO 대역이나 독립 UI 작업을 할 수 있지만 실제 통합 완료로 표시하지 않는다. 기존 클라이언트 기본값/오류/저장 호환과 운영 반영 순서를 함께 정의한다.
6. push는 기능 브랜치·커밋·범위를 제시해 승인받은 뒤 정확한 대상 ref로만 한다. 무인자 push/--all/--mirror·main 대상 push는 금지한다. PR은 기존 정책대로 사용자가 생성하고 에이전트는 제목·본문을 준비한다. PR 생성·CI 통과만으로 병합하지 않는다.
7. main 통합은 승인된 PR 경로만 사용한다. 로컬 main은 이미 병합된 origin/main의 fast-forward-only 동기화만 허용한다. 두 PR의 diff 충돌이 없더라도 API·저장·설정 조합의 의미 충돌을 검토한다. 의존 변경이 main에 들어온 뒤 후행 브랜치의 관련 검사만 다시 한다.
8. 병합 후 자신의 완료 브랜치만 안전 조건을 확인해 정리한다. 다른 담당·사용자 보존 지정·미병합·불확실한 브랜치는 삭제하지 않는다. squash로 안전한 -d가 거절되면 강제 삭제하지 않는다.

### 코드 외의 공유 자원

- **정책 동기화:** AGENTS·CLAUDE·공통 스킬/진입점·이 협업 계획·교차검증 기록은 Git 공유 대상이다. 같은 커밋의 기준본을 읽고 실제 로드한 버전을 대조한다. 계획은 설계 담당만 수정하고 개발자는 결과를 전달한다. 개인 일지·인계·시험 원자료는 공유에 필요하지 않으며 전체 .local, .env, 키, 사용자 대화, 모델/DB 디렉터리를 복제하지 않는다.
- **실제 API/DB 시험:** 브랜치가 달라도 EC2 모델/GPU·DB는 하나일 수 있다. 담당·시간·서버 커밋·클라이언트 커밋·자료 버전·질문/호출 상한을 정하고 적재/삭제/배포/평가를 겹치지 않는다. 데이터 변경 후에는 오래된 평가 기준선을 그대로 사용하지 않는다.
- **Docker:** 독립 clone에서도 같은 daemon의 container_name·포트·볼륨이 충돌한다. 먼저 대역/정적 검사를 사용하고 실제 실행은 한 운영 담당자가 기존 환경에서 한다. 격리 환경을 추가 생성하거나 기존 컨테이너를 내리는 것은 별도 범위다.
- **Chrome:** 실제 설치 폴더·확장 ID·프로필·데이터를 보존한다. 새 clone을 새 확장으로 등록하지 않는다. 검토된 확장 버전을 기존 설치 경로에 반영할 방법과 적용 담당을 먼저 정하며, 상대 작업 소스에 복사해 덮지 않는다. 실제 재로드/UI 시험도 동시에 하지 않는다.
- **배포:** Vercel main 자동 배포가 활성화돼 있으면 PR 병합에도 운영 영향이 있다. PR 준비에 그 영향·EC2와의 버전 호환을 표시한다. EC2 Git 반영/재기동은 PR 병합과 별도 승인 범위로 유지한다.

**Git으로 공유하는 기준본:** AGENTS.md, CLAUDE.md, `.agents/skills` 7개와 그 `.claude/skills` 진입점7개, 이 계획과 `collaboration-plan-review.md`. 공유 docs/design은 각 clone의 Git 기준본을 사용하고 설계에서 갱신한 계약은 이 계획5절을 우선 대조한다. 개발일지 전문·실제 평가 원자료는 자동 복제하지 않는다. 필요한 시험자료만 해당 태스크에서 별도 지정한다.

**스킬 선택:** Codex 기본 git-workflow+backend-pytest, 관리자 화면(W02·W14·W15·W16) 변경이면 vercel-workflow, DB 스키마·쓰기(W02-B 제도/부서 준비·W14·W15 포함)면 supabase-workflow, 승인 운영 실행이면 docker-workflow. Claude 기본 git-workflow+extension-workflow. 설계는 project-design+git-workflow를 사용한다. 모든 스킬을 매번 전부 읽지 않는다. Claude 진입점은 규칙 사본이 아니라 공통 `.agents` 파일을 읽는 연결이다.

**업데이트 전달:** 정책 작성자는 설계 담당 하나다. 변경 파일·최신 시각·커밋을 전달하고 담당은 다음 쓰기 전에 승인된 Git 경로로 자기 브랜치에 반영한다. 교차검토 중 미병합 정책은 읽기 리뷰만 하며 제품 코드에 섞지 않는다. 구현 중 해당 규칙에 영향이 있으면 안전한 작업 경계에서 반영하고 기존 변경을 되돌리지 않는다. 개발자는 계획/일지의 사본을 수정하지 않고 결과를 설계에 전달한다. 실측 결과는 태스크별 자기 `.local/co-op/<태스크>/<커밋>/`에 보존한 뒤 필요한 비민감 근거만 설계가 통합한다.

### 실제 Chrome 적용과 공유 운영 담당

- 기본 운영 담당은 Codex 개발 세션 한 곳이며, Claude는 확장 실제 UI 시험을 맡되 설계가 지정한 시간에만 한다. EC2/DB/Chrome의 다른 시험과 겹치면 대역 검사부터 한다.
- 기존 사용자 확장은 각 기기에서 실제 확인한 설치 경로·ID·프로필을 유지한다. 이 기기의 기존 경로는 `welfare_helper/Extension`이며 다른 기기의 설치 상태를 이 경로로 단정하지 않는다. 새 개발 clone을 기존 사용자 프로필에 추가 등록하거나 상대 소스를 덮어써서 시험하지 않는다.
- 현재 설계 checkout에서 설치 확장 코드를 새 버전으로 바꾸려면 **기존 docs/Co-op의 보존할 공유 문서 커밋이 main에 반영됐는지 먼저 확인**한다. 이후 tracked 변경이 없는 시점에 검토된 origin/main 기준의 다음 docs 전용 브랜치로 기준을 갱신하는 방식으로 기존 설치 경로의 코드를 맞춘다. 이미 병합된 코드의 기준 동기화이며 이 경로에서 기능을 새로 구현하는 것은 아니다. 미병합 문서를 버리거나 원래 브랜치를 reset하지 않는다. 이 준비가 안 되면 설치본 UI 시험만 대기한다.
- 실제 UI 적용 전에는 원래 설치 경로의 Extension 해시와 검토한 main 해시를 비교하고 다시 로드/F5한다. 개별 기능 PR의 대역 검증은 각 clone에서 하고 관련 UI 변경을 모아 한 번의 실제 확인으로 연결할 수 있다. 그동안 실제UI는 미확인으로 기록한다.
- EC2는 최신 main이라고 자동 pull/재기동하지 않는다. 운영 담당이 서버 SHA·설정·DB 자료 버전·평가 상한을 적어 기존 범위별 승인을 받은 뒤 수행한다. Vercel main 추적의 자동 배포 영향은 PR 본문에도 적는다.

### 담당별 기능 브랜치와 합류 순서

아래 명칭은 생성 예정이며 실행된 브랜치가 아니다. 검증만으로 끝나 코드가 바뀌지 않으면 빈 커밋/PR을 만들지 않는다. 한 W항목에 서버·확장 PR이 따로 있으면 둘의 완료 상태도 따로 적는다.

**담당별 단일 개발 큐:** 아래 순번은 계획이며 실제 branch 생성/실행은 하지 않았다. 각 담당은 자기 앞 기능의 내부검사·리뷰·PR 통합을 마친 뒤 다음 기능을 시작한다. 실제 UI를 묶어 시험하는 항목은 미확인으로 별도 추적한다.

- **Claude:** W00 → W06 → W07 → W09 → W08 → W10 → W13 → W05 → W04 최종 확인 → W16 확장 디자인. W03 기본/W11/W14/W15의 기존 소비자 확인은 선행 서버 PR 후 짧은 검토로 끼워 넣는다. 새 contacts 필드가 실제 필요한 경우만 별도 W03 표시 PR을 배정한다.

**병렬 가능한 첫 구간:** Codex W01/W02의 계약·대역 확인과 Claude W00/W06. **병렬 금지:** 같은 담당의 두 기능, Extension 파일 공동 수정, 업로드 중 실제 RAG 품질 평가, 서버 배포 중 다른 담당 실제 종단 시험. 운영 검증 대기는 로컬 독립 작업까지 일괄 중단하라는 의미가 아니다.

### 공통 개발 시작·검증·완료 절차

각 아래 개발 지시에는 기존 계획/실행/검증/테스트에 더해 브랜치, 읽을 코드, 수정 허용 파일, 순서, 최소 검사와 인계물을 지정한다. 파일 목록은 전체를 반드시 수정하라는 뜻이 아니다. 결함이 없으면 검사 결과만 남기며 리팩토링으로 범위를 채우지 않는다. 신규 예정 파일은 구현할 때만 만들고 지금은 생성하지 않는다.

- **시작 기록:** 태스크ID/작성자/리뷰어/clone/branch/base SHA/허용 파일/정책 SHA/운영 호출0 또는 승인 범위. 상대 담당은 읽기 리뷰, 설계가 최종 판정·일지 작성.
- **내부 검사 실행:** 각 clone 루트에서 `node --test <아래 지정 파일>`을 실행한다. Python은 프로젝트 Python3.12와 잠금 의존성을 사용하고, 아래 환경파일 미사용 진입으로 지정 파일만 실행한다. 전역 설치나 원래 프로젝트 venv를 복제하지 않는다. 실제 DB/모델 접근 없는 대역을 확인한 뒤 실행한다.

```cmd
python -c "import os; from BackEnd.core.settings import Settings; names={n.casefold() for n in Settings.model_fields}; [os.environ.pop(k,None) for k in list(os.environ) if k.casefold() in names]; Settings.model_config['env_file']=None; os.environ['HF_HUB_OFFLINE']='1'; os.environ['TRANSFORMERS_OFFLINE']='1'; import pytest; raise SystemExit(pytest.main(['-q','BackEnd/tests/대상파일.py']))"
```

위 `대상파일.py`는 실행 전에 아래 실제 파일명으로 바꾼다. 이는 CI의 환경파일 차단 패턴을 사용한 **예정 명령**이며 이번에 테스트를 실행한 결과가 아니다. 기존 테스트가 DB/모델을 실호출하면 대역 경계를 먼저 수정하거나 해당 검사만 별도 승인 단계로 뺀다. 관리자 UI 검사는 envFile:false인 기존 CI 진입점 `npm --prefix FrontEnd run test:ci -- <src/...test.tsx>`로 지정하고 변경된 관리자 코드에만 `npm --prefix FrontEnd run build:ci`를 실행한다. 빌드 주소는 시험용 비밀 없는 값이며 실제 운영주소 확인을 대신하지 않는다.

- **완료 구분:** 로컬 구현/집중검사/리뷰 완료 → 기능 로컬 커밋 → scope별 push 승인 → 사용자 PR/병합 → 승인 운영 반영/관련 실제 확인. 실제 시험 대기 상태를 기능 전체 실사용 합격으로 적지 않는다. 각 담당의 다음 기능은 선행 PR 병합과 필수 계약검증 완료 후 시작하며, 묶어서 실시하는 실제 UI는 미확인으로 추적한다.
- **인계 형식:** `태스크·브랜치·base/head / 변경파일 / 동작변경 / 검사명령·실패후수정 / 실제확인여부 / API·저장호환 / 남은준비 / 다음선행조건`. 실패 원출력은 자기 태스크 산출물 경로, 비밀/사용자 상담은 제외. 설계가 이 문서7절과 개발일지에 통합한다.

### W08. 오래된 자동 대화맥락 제외 · 요청8

**계획:** 화면의 과거 대화는 보존하되 장기 미사용 뒤 첫 질문에는 옛 상담의 history·요약·documentIds·사용자 조건을 자동 첨부하지 않는다. **30일은 검토용 후보이며 확정 TTL이 아니다.** 정확한 간격은 착수 전 결정한다.

**범위·담당:** Codex 맥락 DTO·서버 소비 경계, Claude 로컬 메시지/전송/저장 경계. 기존 `createdAt`, `topicStart`를 우선 재사용한다. 새 DB 대화 저장은 추가하지 않는다.

**실행:** 미착수. 기준은 화면을 열거나 UI 설정을 바꾼 시간이 아니라 마지막 실제 사용자 발화 시간이다. 현재 새 질문을 넣기 전에 간격을 판정하고 새 활성 상담 경계를 저장해, 첫 요청 실패/취소 뒤 재시도에도 오래된 문맥이 살아나지 않게 한다. 같은 날 주제 전환은 기존 준비 LLM 경계를 유지한다. 타임스탬프가 없거나 미래값이면 과거 맥락 자동 사용을 보수적으로 제외하고 기존 기록은 남긴다.

**검증:** 가짜 시계로 기준 직전/정확히 기준/기준 이후, 페이지 반복 열기, 실패 후 재전송, 재시작 복원을 확인한다. 제외 대상은 서버/클라이언트 한쪽 history만이 아니라 요약·참조ID·직접 조건까지 포함한다. 시간이 지났다는 이유로 내 정보를 삭제하지 않으며 내 정보의 RAG 미사용도 유지한다.

**테스트·완료 기준:** 시간이 지난 시험 상담을 표시한 상태에서 새 질문의 실제 요청 payload와 준비/생성 입력에 옛 서비스·조건이 없음을 확인한다. 실제로1개월을 기다릴 필요는 없다. 화면에서 보존하는 최근30문답 제한과 맥락 제한을 서로 혼동하지 않는다.

### W13. 내 정보를 LLM에 함께 제공할지 선택 · 추가요청3

**담당·허용 파일:** Codex `BackEnd/main.py`, `documents/context.py`, `qa.py`, `tests/test_extension_profile.py`, `test_conversation_context.py`, `test_welfare_qa.py`; Claude `Extension/profile.js`, `protocol.js`, `worker.js`, `offscreen.js`, `content.js`, `conversations.js`, `conversation-store.js`, `conversation-panel.js`와 대응 profile/context/worker 검사. **선행·실행:** W03 기존 부서 키/연락처 출처 연결 → W15 관리자 인증 계약 → W14 합성 저장소·API·관리자 UI 순서다. W13 구현 완료는 선행 조건이 아니다. 실제 DB 스키마/쓰기는 별도 승인, 보존기간·고지/동의·운영 활성화 기준은 해당 단계 전에 확정한다. 제품 구현/DB 작업은 미착수다.

**기록 경로:** 최초 범위는 공개 사용자 `/chat`의 정상 최종 응답에 한정한다. 공통 answer_document를 호출했다는 이유만으로 기록하지 않는다. 관리자·비공개 질의, debug 진단, 사용자 요약, 화면 안내, 내부 대역/평가는 제외하고 취소/실패/검증 탈락 응답도 기록하지 않는다. 기록 API는 클라이언트에 따로 열지 않고 관리자 조회만 인증된 서버 경로로 제공한다. 응답 직전 연결이 끊기면 실제 수신 여부를 보장할 수 없다는 서버 생성 지표의 한계를 유지한다.

**안내 판정:** 단순히 검색 결과에 전화번호가 있거나 서버가 fallback 카드를 붙였다는 이유로 기록하지 않는다. 기존 한 번의 생성 호출에서 LLM이 실제 안내할 연락처를 제공된 후보 ID로 선택하도록 하는 최소 구조화 계약을 사용한다. 후보는 W03이 검증한 부서·번호·출처에 한정하고, 서버는 허용된 선택 ID를 최종 표시 contacts와 기록에 동일하게 연결한다. 사용하지 않은 후보, 일반129, 무효 ID, 모델이 만든 번호, 무연락처/실패 응답은 기록0건이다. 문장 내 전화번호 정규식 검출이나 별도 판정 LLM 호출은 추가하지 않는다. 선택·본문·표시의 일치 여부는 합성 생성 출력 검사와 대표 실제 응답으로 확인하고, 코드가 의미 정확도를 보장한다고 주장하지 않는다. 현재 contacts가 답변과 무관하게 자동 포함되는 경로가 있으면 W03 기본 동작과 이 기록 조건을 구분한다.

**최소 저장 계약:** 서버 발급 `response_id`, 기존 `department_id`, 안내된 업무 연락처 식별자/표시명·전화번호, `contact_version`, 증명 출처 URL·해당 문서 ID/버전, 서버 UTC 생성시각만 저장한다. 문자열은 검증된 카탈로그/원문에서 가져오며 LLM의 자유문을 그대로 저장하지 않는다. IP·브라우저·개인/기기/대화 식별자는 이 테이블에 넣지 않는다. 기존 보안 로그 수집 정책을 새 통계 목적의 추적으로 확대하지 않는다.

**집계 계약:** 최초 범위는 ‘서버 생성 연락처 안내 건수’다. 익명 공개 요청 기준이므로 실제 이용자 수·화면 수신 수·전화 발신·신청 수가 아니다. 한 응답의 같은 연락처는 한번만 저장하고 부서 집계는 `(response_id,department_id)`당1건이다. 같은 부서에 두 연락처가 있으면 이력에는 두 연락처, 부서 횟수는1이다. 서로 다른 부서2개면 각1건이며 전체 안내 응답 수는 response_id의 distinct 수다. 같은 응답의 재기록·F5·복원·다시 저장은 증가시키지 않고, 별도 새 질문으로 생성된 새 응답은 별도 건이다. 기존 rate/gate를 유지하고 사용자 식별을 추가하지 않는다. 클라이언트 수신 확인 API나 임의 부서 ID 전송은 만들지 않는다.

**보존·실패:** 관리자는 날짜/부서 필터·페이지 목록·집계를 조회한다. 한국 시각의 기간 필터를 UTC 경계로 일관되게 변환한다. 보존기간 만료/관리자 삭제 시 같은 원시 안내 기록에서 산출한 통계도 함께 줄이며 별도 영구 누적 카운터를 만들지 않는다. 보존기간과 삭제 권한/UI는 계약 확정 항목이다. 기록 쓰기는 남은 요청기한 안의 유한한 별도 예산으로 제한하고 실패해도 정상 답변은 제공한다. 실패 메타데이터만 남겨 집계 누락을 알리며 원문을 로그에 쓰거나 무한 재시도하지 않는다. 유실 없는 비동기 집계가 필요하면 별도 outbox/큐·재시도 계약이 필요하므로 무관리 background task를 대신 추가하지 않는다.

**검증·테스트:** 공개 chat만 기록하고 관리자/debug/요약/화면/실패는 기록하지 않음, 비관리자 조회/집계 차단, 세션 만료, 허용 필드만 저장(본문/쌍/프로필/요약/임의 필드 없음), 후보 존재하나 미안내0건, 실제 선택 연락처만 저장, 무효/129/무연락처0건, 동일 response 중복, 같은/다른 부서 집계, 날짜 경계·페이지·삭제/만료, 저장 실패/지연 시 답변 지속을 대역으로 확인한다. 실제 운영 시험은 승인된 합성 질문으로만 하며 모델 선택·실제 응답·저장 행·집계를 나누어 보고한다.

### W15. 기존 비밀번호 인증 후 새 비밀번호 발급 · 추가요청5

**계획:** 관리자 설정에서 현재 비밀번호를 다시 입력해 인증한 뒤 ‘새 비밀번호 발급’을 누르면 지정 형식의 무작위 새 비밀번호를 발급하고 이후 로그인에 사용한다. **현재 비밀번호를 모르는 경우의 복구는 범위 밖**이다. 정규식은 발급 형식 검사에만 사용하고 서버의 안전한 난수 함수로 생성한다. 길이·문자종류는 교차검토 뒤 확정한다.

**담당·파일:** Codex `BackEnd/admin/session.py`, 신규 예정 `BackEnd/admin/credentials.py`, `BackEnd/tests/test_admin_password_rotation.py`, 기존 `test_admin_auth_runtime.py`; `FrontEnd/src/api/auth.ts`·검사, `pages/AdminPage.tsx`·검사 또는 독립 신규 `components/admin/PasswordRotation.tsx`·검사. 영속 저장을 채택하면 Codex 소유 DB migration을 추가한다. `core/settings.py`·`.env.example` 변경이 필요하면 계약에 명시하며 실제 .env는 읽거나 편집하지 않는다. 확장 코드 변경은 기본 범위에서 제외하지만 Claude의 소비자 검토는 필수다. 기존 `Extension/tests/admin_auth.test.cjs`, `admin_content.test.cjs`에서 구세션401→재로그인 안내와 새 비밀번호 옵션 로그인을 대역 확인한다. 실제 결함만 Claude 후속 브랜치에 배정한다. 생성 형식은 옵션 입력의 최대256자 제한과도 대조한다.

**실행·저장 제안:** 현재 공통 비밀번호는 서버 설정, 세션은 프로세스 메모리에 있어 새 값을 UI에만 표시하거나 메모리에만 넣으면 재시작 후 유지되지 않는다. 관리자 전용 영속 저장소의 해시+credential_version으로 원자 교체하는 안을 검토한다. 최초 전환 때만 기존 설정 비밀번호를 검증하고 영속 전환 후 저장소 오류를 옛 비밀번호로 fallback하지 않는다. 해시 방식·저장소·이관·복구를 확정한 뒤 구현하며 현재 실행은 미착수다.

**인증·원자성:** 기존 관리자 세션만으로 발급하지 않고 현재 비밀번호 재인증을 요구한다. 재인증을 두 요청으로 나누면 짧은 수명·1회용·해당 세션에 묶인 발급 권한을 사용한다. 인증 실패는 제한하고 현재 비밀번호/새 비밀번호를 로그·URL·localStorage에 남기지 않는다. 발급 완료는 해시 교체 성공 뒤에만 표시한다. 실패 시 기존 비밀번호를 유지하며 동시2발급은 버전 비교로 하나만 성공시킨다. 기존 세션 무효화 후 새 비밀번호 재로그인을 권장안으로 검토하고, 사용 중인 문서 작업에는 인증 변경과 작업 중단을 혼동하지 않도록 명시한다.

**실패·검증·테스트:** 잘못된 기존 비밀번호, 만료/재사용 발급 권한, 형식/난수 생성, 동시 발급, 저장 실패, 재시작 후 새 비밀번호 유지·구비밀번호 거절, 이전 세션 처리, 응답 유실을 확인한다. 교체 후 응답 유실 시 사용자가 새 값을 못 받을 수 있으므로 최종 적용/표시·복구 UX를 구현 전에 확정한다. 별도 ‘확인 후 적용’ 버튼은 가능한 해결안이지 이미 승인된 요구가 아니다. 이전 설정값으로 조용히 되돌리는 복구는 금지한다. 실제 발급 시험은 운영 관리자 접근을 바꾸므로 별도 범위 승인이 필요하다.

## 5. 공유 계약과 검증 방식

### 기능 연결 전에 확정할 계약

- **W03 연락처:** 신규 응답은 검증된 서비스 담당만, 기존 저장분의 일반 연락처는 복원 호환. 출처 URL·문서 버전·검토일 의미, 빈 연락처를 구분한다. 응답 필드를 바꿀 때 기존 확장의 표시도 함께 정의한다.
- **W08 맥락:** 비활성 기준시각·상담 경계·누락 timestamp 처리, history/summary/userMessages/documentIds를 같은 범위로 제한, 실패 후 경계 유지. 클라이언트 시간은 권한 근거로 사용하지 않는다.
- **W10 요약:** 4절의 신규 `/api/v1/conversation/summary` 계약을 사용한다. 기존 chat 응답에 섞지 않고 공개 상담의 완전쌍 최대 60메시지/12000자·출력 1200자·LLM 최대 1회·검색 0회, 메모리 표시만을 초기 범위로 한다. 아래 호환 순서대로 반영한다.
- **W06/07/09 UI:** 도킹/자유배치와 크기/투명도 설정, 음성입력과 낭독의 배타 처리, 저장키/버전/초기값. 광범위한 브라우저 권한을 추가하지 않는다.

### 구현할 계약 버전과 결합 검사

- [문서 목차](../README.md), [현재 전체 구조](../design/architecture.md), [현재 RAG](../design/rag.md), [현재 확장](../design/extension.md), [현재 관리자](../design/admin.md)를 함께 읽는다.

모바일·음성 API 근거(확인일2026-11-04):

- [Claude Code 공통 지침 import](https://code.claude.com/docs/en/memory#import-additional-files): CLAUDE.md에서 프로젝트 내부 AGENTS.md를 불러오는 연결에 사용했다. 스킬 본문은 필요한 작업에서만 해당 파일을 직접 읽도록 연결했다.
