### S1. 팀원 스트리밍 구현의 남은 계약·결함 보완

**상태:** S1 로컬 보완 완료(7ec23c3), S2 로컬 집중검사 완료. 팀원 원본 c9abd74를 main/a497bb1 기반 codex/fix-chat-stream에 이력 보존 merge한 뒤4파일만 보완했다. CI 목록 누락·최상위status확인·실제 재현된 기한후늦은초안 전송을 수정했다. PR #33으로main/6e808d7통합완료, 최종head56d7f2f의원격CI4job성공. 후속S3에서main/c15fb9e운영API반영과점진전달1건확인을완료했다. [결과와 한계](devlog.md#log-20261115-s1-result)

현재 구현은 Ollama 최종 생성 조각 → `DraftStream`의 JSON text 추출 → FastAPI `/api/v1/chat/stream` NDJSON → 확장 offscreen/content 및 React 공개 웹 표시다. `accepted`, `draft(text 또는 append)`, `final(response)`, `error(status/detail)` 이벤트를 사용한다. 최종 응답은 기존 검증·연락처 기록 경로를 거치고 초안은 최종 답변으로 대체한다. 기존 `/api/v1/chat`은 유지하며 404/405의 정해진 오류일 때만 구 경로로 한 번 요청한다.

**구체적으로 해결할 항목:**

1. **새 서버 검사가 CI에서 빠져 있다.** `BackEnd/tests/test_chat_stream.py`는 추가됐으나 `scripts/ci_python.py`의 명시 파일 목록은 미변경이다. 해당 파일을 CI 대상에 넣어야 한다. 해당 SHA에 연결된 PR-triggered workflow 조회 결과는 0개이며 로컬 실행 보고도 이번에 받지 못했다. 테스트 코드 존재를 통과로 적지 않는다.
2. **JSON 필드 순서에 따른 범위 밖 초안 노출 가능성.** `DraftStream.feed`는 status가 없더라도 text를 전송하고, 발견한 status가 out_of_scope일 때만 중단한다. 예를 들어 text가 먼저 온 다음 status가 out_of_scope로 완성되면 앞선 초안은 이미 전송됐을 수 있다. 일반 JSON은 키 순서를 보장하지 않는다. 표시 가능한 status 확인 후 초안을 내보내는 최소 수정과 text-first/분할-status 사례를 우선 검토한다. 정적 코드에서 찾은 경로이며 실제 운영 재현은 하지 않았다.
3. **종료·취소 검증 공백.** 새 라우트는 daemon thread와 asyncio queue를 사용한다. 기존 disconnect Event/gate를 공유하는 것은 확인했으나, accepted 전 단절·초안 도중 취소·final 직전 단절의 새 경로에 대한 실제 슬롯 반환/늦은 출력 차단은 별도 확인이 필요하다. 결함으로 단정해 새 취소 프레임워크를 만들지 말고 기존 실행 계약 검사에 스트림 사례를 연결한다.
4. **검증 전 초안의 공개 범위 확정.** 초안은 최종 source ID·문서 버전 검증 전에 사용자에게 간다. final 실패 시 UI가 초안을 제거해도 이미 본 내용을 되돌릴 수는 없다. 초안은 표시 전용으로 유지하고 저장·요약·낭독·연락처 기록은 final 성공에만 연결한다. 기존 개인정보 마스킹이 숫자/escape 청크 경계에서도 유지되는지 확인한다. 최종 응답을 사실 정확도까지 “검증된 답변”이라고 표현하지 않는다.

**범위:** API 서버·LLM 어댑터·확장·React 공개 웹이다. 관리자 문서별 query, 수동 요약, DOM 안내, Desktop 스트리밍은 현재 팀원 변경에 포함되지 않으며 자동 추가하지 않는다. 서버와 클라이언트를 같은 PR에 유지한다면 공유 계약 검토 및 서버 우선 배포 순서를 명시한다. 분리할 필요가 있을 때만 작성자와 PR 범위를 정한다.

**담당 제안:** 기존 브랜치 작성자가 수정하고 설계가 읽기 리뷰한다. 별도 담당을 지정하면 파일 소유권부터 인계한다. 이번 검토에서는 상대 브랜치를 checkout/수정하거나 개발 착수를 메시지로 지시하지 않았다.

2. 서버 스트림 경로를 먼저 준비하고 웹/확장 소비자를 적용한다. Vercel 자동 배포가 먼저 되면 기존 JSON fallback으로 계속 작동하는지 S2 근거를 확인한다.
3. 기존 HTTPS를 통과하는 질문 1건에서 요청 시작, accepted, 첫 **비어 있지 않은 draft**, final 도착 시각을 각각 측정한다. accepted 즉시 수신만으로 답변 스트리밍 성공이라 하지 않는다. UI에서도 final 전 초안이 갱신돼야 한다.
4. FastAPI 직접 연결에서는 분할 도착하지만 Caddy 경유에서 한꺼번에 온다면 실제 버퍼링을 확인한 뒤 프록시 최소 설정 변경을 별도 범위로 처리한다. X-Accel-Buffering 헤더만으로 Caddy의 즉시 전달을 단정하지 않는다.
5. 준비/검색·리랭커가 끝나기 전에는 아직 답변 초안이 없다는 구조적 한계를 기록한다. 스트리밍은 총 생성시간이나 검색 병목을 자동 단축하지 않는다. 지연 문제가 남으면 이 최초 측정으로 느린 단계를 좁히고 그때만 최적화한다.

**남은 지연 확인:** 이cold단건은생성구간166.470초(검색19.191/리랭킹12.900초)로길었다. 추가호출전원자료의로드/프롬프트/생성구분과측정범위를정한다. 상주후동일질문성능은이번에측정하지않았으며추가워밍업/모델변경을자동실행하지않는다.

**완료 기준:** EC2 적용 SHA/이미지와 소비자 버전이 명확하고, 기존 HTTPS에서 final 이전 draft 수신·최종 교체·관련 취소가 확인된다. 서비스 healthy·HTTP200만으로 끝내지 않는다. 이전의 30→50→60초 목표는 별도 전체 응답 시간 지표이며 새 첫 초안 SLA를 임의로 만들지 않는다.

### S4. 추천질문 로직 최소 개선

**상태:** F6 검토만 완료, 구현 미착수. [확인한 문제](devlog.md#log-20261110-1147-menu-review).

현재는 고정 추천 3개이며 과거 assistant 메시지 존재로 후속형을 고른다. 자료없음 응답 뒤에도 “그 서비스”가 나오거나, 7일 만료/정보 OFF로 자동 맥락이 초기화돼도 화면 기록 때문에 후속형이 유지될 수 있다. 타인 상담의 대상과 무관하게 본인 저장 조건이 추천 초안에 붙는 문제도 있다.

실행 계획:

1. 유효한 최신 상담 맥락과 서비스 참조가 있을 때만 후속 질문을 제시한다. 기록 존재만으로 결정하지 않는다.
2. 대상이 불명확하거나 본인과 다른 상담 대상이면 저장된 본인 조건을 덧붙이지 않는 일반형을 사용한다. 문항별 정규식 대상 판별기를 만들지 않는다.
3. OFF에서도 사용자가 선택한 추천 초안에 조건이 들어가는 현재 동작은 자동 프로필 전송과 다르다. OFF가 추천 개인화까지 막아야 하는지는 미확정이므로 구현 전 한 번 결정한다. 권장안은 OFF일 때 일반형 추천이다.
4. 추천 선택은 입력란만 채우고 자동 전송하지 않는다. 작성 중 초안/오래된 버튼의 revision 보호를 유지하며 새 LLM 추천 호출을 추가하지 않는다.

**변경 후보:** `Extension/input-assist.js`, 상태를 전달하는 `content.js`, 관련 기존 검사. **완료 기준:** 최초 질문·정상 후속·근거 없음·맥락 만료·OFF·다른 대상에서 추천이 유효하고 기존 입력을 덮지 않는다. 이 항목의 구현은 후속 태스크 배정 후 시작한다.

### S5. 남은 실제 사용자·관리자 확인

구현 완료와 실제 확인을 구분한다. 이미 사용자가 정상 확인한 F1~F3 및 기본 주제전환/정보필터링을 무조건 재시험하지 않는다. 스트리밍·추천 변경에 직접 영향받거나 아직 확인 기록이 없는 경우만 다음 묶음으로 처리한다.

1. **확장:** 같은 설치/프로필 유지, 재로드 후 스트리밍 표시·취소·final 저장 연결을 확인한다. F7 전체 질문 주제의 짧은 요약, F8 최종 ON/OFF 전송은 최신 버전 사용자 확인 기록이 남아 있는지 먼저 대조한다. 이미 확인됐으면 제외한다.
2. **공개 DOM/음성:** 남아 있는 실제 복지로 요소 강조·가림/스크롤·없는 요소 처리와 한국어/숫자/연락처 낭독·마이크·중지 확인만 수행한다. 실제 청취·기기 마이크 권한은 사용자에게 맡기고 접근 가능한 UI 조작은 개발 담당이 수행한다.
3. **관리자 UI:** production 로그인 뒤 문서 상태·검색·연락처 기록 페이지가 열리는지 확인한다. 기존 서버 API·PDF 처리 성공을 반복 적재로 확인하지 않는다. UI 업로드 확인이 필요하면 허용한 test_only 자료 1건과 정리 범위를 먼저 정한다.
4. **W14 실제 첫 기록:** 정상 공개 상담에서 검증된 연락처가 반환된 경우, 관리자 조회/집계에 예상 부서·번호가 한 응답당 맞게 연결되는지 확인한다. 질문/답변/프로필/IP가 이 기록에 저장되지 않는 계약을 유지한다. 수집 ON 이전 대화를 소급 생성하지 않는다.

**완료 기준:** 각 미확인 항목에 사용자 확인 또는 실제 담당 관측·버전·결과가 남는다. 실패가 없으면 제품 코드를 바꾸지 않는다. 전체 데이터 삭제/확장 재설치를 시험 준비로 사용하지 않는다.

## 4. 지금 자동 재개하지 않을 잔여

### H1. RAG 의미 정확도: 실제 실패, 보류 유지

과거 실제 생성에서 문서에 없는 지급일 생성, 질문 항목 누락, 조건/예외 논리 혼동이 관측됐다. B안도 11월 9일 첫 실제 평가에서 지급일 질문을 나이 설명으로 바꾸고 국적·예외 요건을 잘못 결합해 실패했다. “검증 안 됐을 뿐인 후보”보다 정확히는 **첫 평가에서 실패해 채택하지 않은 후보**다. [실패 근거](devlog.md#log-20261109-1307-d43ea6).

재개 지시가 있으면 현재 main과 보존 원문/정답표를 기준으로 실패 단계(검색 원문 누락/프롬프트 입력/생성 논리)를 먼저 나눈다. 동일 조건의 최소 실패 사례로 후보 하나만 비교하고 결과를 보존한다. B안 적용, 새 모델, 문항별 문자열/숫자 필터, 성공할 때까지 재질문을 기본 해결책으로 삼지 않는다. 스트리밍 완료와 정확도 합격은 별개다.

### H2. 별도 연락처 CSV/W03: 사용자 자료 대기

별도 파일 경로·접근 링크가 아직 없다. 기존 공공 서비스 CSV로 대체하지 않는다. 자료가 주어지면 필드·기관/부서 키·중복·제도 연결·미매핑을 읽기/dry-run으로 확인한 뒤 승인된 범위만 적재한다. 원문에 있는 연락처 안내와 현재 W14 수집은 이 별도 자료를 기다리지 않는다.

### H3. 복구·비밀번호·기기 전환: 별도 필요 시

pgvector 이미지 다운로드, worker/DB 복구 자동시험은 명시 보류다. production 비밀번호 회전과 실제 EC2 재부팅도 미실측이지만 시연 완료의 새 필수 조건으로 만들지 않는다. 로컬로 실제 전환할 때만 기존 README의 CPU/GPU·모델 환경 단계와 HTTPS 전용 클라이언트 경계를 다시 정한다. 지금 로컬 제품 연결을 복원하거나 Caddy/systemd를 리팩토링하지 않는다.

## 5. 착수·인계·완료 운영

각 S단계 시작 때 주 작성자/검토자·root/branch·기준 main·허용 파일·계약·완료 기준을 handoff에 적는다. 설계는 문서/리뷰, 배정된 개발은 코드/실행을 맡으며 같은 checkout을 동시에 편집하지 않는다. 같은 기능 브랜치에서 최소 수정→관련 검사→리뷰→선별 커밋 순서로 진행한다. 공유 계약/서버를 먼저 검토하고 소비자와 결합한다.

단계가 끝나면 이 파일의 상태와 merge_plan의 요약/일지 링크를 갱신하고 실제 실패·정정·검사·미실측은 devlog에만 누적한다. 성공한 검사를 이유 없이 다시 돌리지 않는다. 사용자에게 필요한 결정은 추천 OFF의 의미, CSV 경로, 실제 청취/인증, 구체 운영 범위가 발생할 때만 요청한다.
