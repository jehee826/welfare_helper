## 1. 먼저 알아야 할 현재 상태

**개발은 끝나지 않았다. 자료 적재와 단건 속도 개선은 마쳤지만, 답변 정확도·실제 Chrome·일부 운영 기능 검증이 남았다.** 이 문서는 사용자가 요청한 기기 간 작업 인계용 스냅샷이다. 기존 실행 계획을 대체하지 않는다.

사용자의 마지막 운영 지시는 **“브랜치 업데이트한 거 기존 동작만 재확인하는 것까지만”**이다. **설계·개발 두 세션 모두 해당 작업을 완료해 idle인 것을 확인했다.** EC2의 GitHub 직접 pull·소스 02317bb 동기화·기존 서비스/권한/모델/자료 확인을 마쳤고 추가 이미지 교체·부팅 보완은 적용하지 않았다. 이 종료는 전체 개발 완료가 아니며, **노트북에 담당을 넘긴 뒤 두 기기에서 같은 EC2·DB를 동시에 변경하지 않는다.**

현재 인계 시 확인할 지점은 **데스크톱 최종 기록/공유 → 소스와 실행 이미지의 차이 인지 → 남은 품질·실제 Chrome 검증의 다음 범위 결정**이다. 이전 부팅 보완안을 자동 재개하지 않는다. 자료 356개를 다시 올리는 단계가 아니며 모델 추가 다운로드나 전체 Docker 재설치부터 시작하지 않는다.

### 담당·변경 권한·개발 환경

현재 전체 제품의 담당은 Codex다. 기존 Claude의 Extension 담당 제한은 이번 통합 수정에서 Codex로 이전했으며 Claude 세션/PR의 완료를 기다리지 않는다. 다만 **설계 세션은 요구·검토·기록, 개발 세션은 제품 코드·실행 시험**으로 나눠 순차 수행했다. 노트북에서 두 세션을 유지한다면 파일 작성자와 실행 담당을 하나로 정하고 checkout/index·공유 운영 작업을 동시에 조작하지 않는다.

이번 작업 브랜치는 `codex/fix-merge` 하나이며, 과거 `codex/develop` 기능 PR 흐름은 끝났다. 기능 수정·필요 검사·선별 커밋 후 최종 main PR로 통합할 계획이다. **main 직접 수정/commit/push·PR 우회 병합·worktree·무조건 reset/clean/강제 push는 금지**한다. 사용자가 최종 PR을 검토·병합 승인하며 현재 fix-merge 최종 PR 생성/병합은 하지 않았다.

Python 3.12·Node.js 22 기준으로 기존 Docker 격리 검사를 사용했다. 로컬 생성 모델은 필요하지 않고 Windows 호스트에 Linux 전용 잠금을 직접 설치하지 않는다. 필요한 도구가 이미 있다고 가정하지 말고 `pyproject.toml`·`.python-version`·`FrontEnd/package.json`·`requirements/README.md`·기존 CI 명령을 확인한다. 모든 운영 서비스를 띄우는 대신 모델/DB 없는 최소 검사부터 실행한다. 이 인계 작성은 새 의존성 설치·시험 실행 요청이 아니다.

실제 `.env`·키·비밀번호·토큰·비밀 URI를 읽거나 출력하지 않는다. `.env.example`과 승인된 런타임 주입을 사용하고 새 기기에서는 지원되는 로그인/인증만 요청한다. 전체 `.local`·모델·DB·Chrome 저장소 복사를 선행 조건으로 삼지 않는다. 과거 속도 개선 태스크의 포괄 승인을 W14 DB 적용·W15 인증 전환·새 배포로 확대하지 않는다.

## 3. 가장 최근 EC2 작업의 정확한 중단 지점

1. 사용자 요청은 EC2 재시작 때 최신 서비스가 정상 등록되게 보완하고 EC2 checkout도 `codex/fix-merge`로 맞추는 것이었다.
2. 원래 EC2 소스는 `codex/fix-rag-normal-flow`의 `793aca6`이었고, 실제 컨테이너는 별도 검증 이미지였다. 따라서 Git 브랜치와 실행 코드가 달랐다.
3. EC2에 비공개 GitHub 저장소 인증이 없어 직접 fetch가 실패했다. 개발 세션은 Git bundle로 **EC2 소스만 `codex/fix-merge`의 `02317bb`로 동기화 완료**했다고 보고했다. `.local`과 기존 자료는 보존했다.
4. 사용자가 별도 인증을 먼저 하겠다고 하여 이후 EC2 변경을 중지했다. 개발 세션 최종 보고는 **실행 컨테이너·부팅 스크립트는 아직 변경하지 않았고, 진행 중 명령 0개, SSH 키/config도 생성·수정하지 않았다**는 것이다.
5. 이후 사용자가 저장소 전용 읽기 Deploy key 등록 완료를 알렸다. 개발 세션은 저장소 한정 SSH 설정·공식 호스트 지문 대조 후 **EC2의 직접 fetch·pull --ff-only 성공**을 보고했고, 원격과 EC2는 모두 02317bb였다. 인증 대기는 해제됐고 부팅 보완을 재개했다. 개인키·토큰은 채팅이나 Git으로 옮기지 않으며 끝난 인증을 반복하지 않는다.
6. 가장 최근 사용자가 **브랜치 업데이트와 기존 동작 재확인까지만**으로 범위를 줄였다. 새 이미지 준비 명령은 실패했고 backend/worker 교체·부팅 스크립트 변경은 실행하지 않았다. **이 제한이 앞선 부팅 보완 계획보다 우선한다.**
7. 개발 세션 최종 결과는 HTTPS health·내부 readiness 200, 익명 관리자 접근 401, 내부 진단의 공개 접근 404, 기존 364문서/921벡터 보존이었다. 기존 1슬롯·Qwen GPU/BGE CPU 상주, 서비스 등록·이미지 핀 일치를 확인했다. **추가 상담 추론·서비스 재시작·실제 재부팅은 하지 않았다.**

향후 별도 운영 작업을 결정할 때 확인할 항목:

- EC2 실제 checkout 경로·branch·SHA와 원격 추적 대상, 후속 작업 뒤에도 GitHub 직접 읽기 인증이 유지되는지. 새 키를 불필요하게 생성하지 않는다.
- 실행 backend/worker 파일이 저장소 SHA 전체와 같은지, 부분 파일 반영 상태인지. **소스 pull 성공을 이미지 교체 완료로 표시하지 않는다.**
- 기존 `welfare-helper.service`와 `start-preserved.sh`의 경로·실행 순서·이미지 핀·환경·마운트. 소스가 최신이어도 구버전 재빌드 경로로 되돌리지 않는다.
- backend/worker 코드 정합성과 부팅 후 기존 두 모델의 빈 입력 사전 로드 보완은 **미적용 잔여**다. 마지막 재확인 지시로 실행 범위에서 빠졌으므로 별도 요구 없이 착수하지 않는다.
- 실제 EC2 재부팅 종단 시험은 미실시다. 서비스 enabled·구문 검사·이미 실행 중인 컨테이너 시작 확인으로 재부팅 성공을 대신하지 않는다.

## 4. 현재 운영 기준과 보존할 경계

- 클라이언트는 EC2 HTTPS를 사용한다. 확인된 주소는 `https://15.164.190.21`이며, 인스턴스 중지/기동 뒤 실제 주소·TLS를 재확인한다. 제품에 localhost/SSH 터널 연결을 복원하지 않는다.
- Qwen 모델: `qwen3:30b-a3b-instruct-2507-q4_K_M`. 임베딩: 기존 `bge-m3`, 1024차원. Qwen GPU 상주·bge-m3 CPU 상주, 최대 적재 2·keep-alive -1·모델 병렬 1·내부 최대 대기 3을 확인했다.
- ctx 16384·출력 상한 1024·thread 8, 기존 f16 KV/Flash auto를 유지했다. 기존 모델/리랭커 파일·태그·가중치·양자화·정밀도를 바꾸거나 새 모델을 다운로드하지 않는다. 과거 q8/Flash 명시 ON 시험은 복구됐으며 재사용할 현재 설정이 아니다.
- 앱 admission gate는 실행 3칸을 유지하며 네 번째는 429다. **Ollama 모델 1슬롯의 내부 대기와 HTTP 요청 전체 FIFO는 다르다.** 앱 FIFO를 추가하거나 HTTP 전체의 완료 순서가 보장된다고 설명하지 않는다. 기한·취소·네이티브 종료 전 gate 보유를 보존한다.
- 속도 시험 당시 클라이언트 600초/서버 900초 요청 예산은 성능 합격 기준과 별개다. 설정 파일의 기본값과 실제 주입값도 구분한다.
- 최근 실측 운영 backend는 **8a289b8 기반에 context.py만 67b8307을 반영한 부분 이미지** `07de146da2389fa447de6d08baa035d34346cbc5b09b472aba2095981cdef64a`다. worker는 2a15ccd 계열, Ollama는 74129cd 때의 기존 이미지, edge는 기존 이미지다. 최신 EC2 동기화 작업에서 실행 이미지를 아직 바꾸지 않았다는 보고까지 확인했다.
- 이미지를 바꾸면 부팅 이미지 핀도 함께 맞춰야 한다. 기존 모델·DB·인증 볼륨·문서·사용자 프로필/상담/Chrome을 보존한다. `docker compose up -d --build`를 현재 운영 주입값·GPU 설정 확인 없이 실행하지 않는다.
- Docling은 문서별 자식 프로세스로 필요할 때 로드한다. worker는 문서 감시와 W14 만료 삭제도 담당하므로 전체를 끄는 방식으로 메모리를 줄이지 않는다.

## 7. RAG에서 반드시 유지할 계약

- **주제전환·후속·나이/대상 정정은 LLM 지침을 우선한다.** 문서명·키워드·숫자별 정규식/정확 문자열 특례로 의미 판단을 묶지 않는다. 권한·개인정보·출처/문서 버전·입력 예산·취소/기한·응답계약은 코드 경계로 유지한다.
- 질문과 직접 발화에 기반해 검색한다. 내 정보는 기본 OFF이며 구 profile은 무시한다. 유효한 현재 프로필·별도 revision 동의를 가진 명시 ON에만 나이·소득·가구·지역·장애 여부 5필드를 **최종 생성에 제공하고 검색·검색 준비에는 보내지 않는다.**
- 검색한 후보를 사용자 조건과 비교해 **일치 안내 / 확인된 불일치는 이유와 함께 추천 제외 / 정보 부족은 추가 질문**으로 나눈다. 모두 불일치해도 현재 조회된 제도 범위로만 설명한다. 별도 판정 LLM이나 문항별 의미 필터를 추가하지 않는다.
- 직접 사용자 발화·최신 정정을 우선한다. 본인 프로필을 손자/어머니 등 타인 대상에게 대입하지 않는다. 이전 챗봇 답변을 새 사실 근거로 사용하지 않는다.
- OFF 전환 시 프로필·화면 기록을 보존하고 history·파생 요약·조건·문서 참조를 포함한 자동 맥락을 새로 시작한다. 마지막 실제 사용자 발화 후 **7일 이상**일 때도 같은 자동 맥락을 제외한다. 저장 schema v3를 v2로 강제 환원하지 않는다.
- 임베딩/검색 성공은 정확한 최종 답변의 증거가 아니다. 금액·예외·기준 사건·신청 시점과 수급 시점을 원문과 대조하고 첫 실패 응답을 보존한다.

## 8. 남은 작업과 권장 재개 순서

1. **기기 인계 마무리:** 최신 원격 SHA·데스크톱 종료/인계 신호·문서 공유 여부를 확인한다. EC2 직접 pull/기존 동작 점검은 완료됐고 실행 이미지는 부분 반영 상태다. 새 부팅/이미지 보완은 마지막 요청 범위 밖이므로 자동 실행하지 않는다. 이미 통과한 health 점검도 구체적 필요 없이 반복하지 않는다.
2. **RAG 정확도 보완·필요 최소 회귀:** 재산 공제를 자격 상한으로 오독, 본인 조건의 타인 혼입, 나이만으로 자격 확정, 원문 밖 지급일/상담시간, 신청/수급 시점·제외 사건 왜곡을 우선한다. 주제전환→후속→최신 정정→타인→OFF 경계와 근거 문서/버전을 함께 확인한다. 이미 끝난 10건/18건을 무조건 반복하거나 전수 1092건으로 확대하지 않는다.
