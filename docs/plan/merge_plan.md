## 4. Vercel·EC2 배포 적합성 검증

### 단계 C. EC2 없이 먼저 마칠 검증

1. Docker의 Python 3.12·Node.js 22 환경에서 변경별 집중 검사 후, 결함/누락 정리가 끝난 시점에 원본 전체 내부 검사를 1회 실행한다. 이후는 변경 영향 범위만 재검사한다. Linux 잠금을 Windows에 직접 설치하지 않는다.
2. 실제 `.env`를 읽거나 마운트하지 않는다. backend는 설정 환경 제거·`env_file=None`·모델 offline·네트워크 차단으로 실행한다. DB 테스트는 격리 합성 DB와 운영 DB를 명확히 나눈다.
3. FrontEnd `test:ci`·`build:ci`, TypeScript·정적 리소스·SPA 경로를 확인한다. 운영 `VITE_API_BASE_URL`은 기존 EC2 HTTPS이어야 한다. CI의 `https://example.invalid` 빌드 통과는 운영 주소 확인을 대신하지 않는다.
4. Compose·Dockerfile·Caddy·잠금 의존성·신규 파일의 이미지 포함·worker 연결을 더미 설정으로 검토한다. `docker compose up -d --build`와 기존 운영 profile/override를 유지하며 비밀값이 치환된 전체 설정은 출력하지 않는다.
5. **모델 설정 주의:** 저장소 Compose의 기본 `qwen2.5:1.5b-instruct`와 기존 EC2 운영 모델 `qwen3:30b-a3b-instruct-2507-q4_K_M`은 다르다. 실제 운영 주입값·기존 GPU/runtime·캐시를 확인하기 전 기본 Compose만 실행하지 않는다. 임의 다운로드/교체는 하지 않는다.
6. 배포 순서별 호환을 확인한다. 새 Vercel UI→옛 API, 새 API→기존 확장, 새 확장→API의 지원 기능/오류 처리를 점검한다. W10/W13처럼 새 계약이 필요한 UI는 서버가 준비되기 전에 사용 가능으로 노출하지 않는다.
7. W14는 `REFERRAL_RECORDS_ENABLED=false`에서 migration 없이 기존 상담이 유지되는지 확인한다. 활성화하려면 `0006_contact_referrals.sql`, 기존 department/document 버전, 수집 고지, backend/worker 동일 설정, 삭제 스케줄 준비가 필요하다. 만료 행은 조회 제외하되 물리 삭제는 worker 중단 시 지연될 수 있음을 확인한다.
8. W15는 `ADMIN_CREDENTIALS_FILE` 미설정의 기존 로그인 호환과, 설정한 영속 해시 파일 경로/권한·초기화·복구 절차를 구분한다. 컨테이너 재생성 때 비밀번호가 사라지는 구성을 배포하지 않는다.

**C 완료:** 내부 검사 실패 0건, 모든 skip의 이유/대체 검증 확인, 최종 계약·마이그레이션·환경 변경 목록·복구 절차 준비. 이 단계만으로 운영 배포 안전 판정을 내리지 않는다.

### 단계 D. 사용자가 EC2를 켠 뒤 실제 검증

EC2 기동은 사용자가 한다. 기동 확인 뒤 필요한 시험 시점에 연결한다. **기동 사실만으로 배포·재시작·DB 쓰기·관리자 비밀번호 교체를 승인받았다고 해석하지 않는다.** 실제 실행 전에 대상 SHA·서비스·호출/자료 범위·변경/복구 영향을 제시해 필요한 범위만 확인한다.

1. **읽기 사전 점검:** 실제 EC2 checkout/image SHA, 실행 backend/worker/edge·모델 식별, 기존 GPU·캐시·볼륨, API 주소/TLS, 현재 활성 문서 버전을 확인한다. 키·환경 전체·비밀번호는 출력하지 않는다.
2. **현재 서버 기준선:** 최소 health와 공개/관리자 접근 경계를 확인한다. 공개 게시 문서만 익명 상담 가능, 진단/비공개/test_only는 차단, CORS·세션·rate/gate를 구분한다. 200 또는 container running만으로 통과하지 않는다.
3. **배포 후보 검증:** 최종 병합 전에 fix-merge의 식별된 후보 SHA를 검증할 수 있는 대상과 반영 방식을 정한다. 기존 운영 서버밖에 없으면 필요한 서비스 반영/중단·복구 범위를 먼저 제시한다. main에 먼저 넣고 나중에 검증하는 순서로 바꾸지 않는다.
4. **데이터 작업:** W02는 대상 문서/제도/버전·기존 게시본 보존을 확정한 뒤 1→9개 순서. W14 DDL/수집 시험은 별도 승인 범위에서 합성 입력으로만 실행한다. 전체 삭제·재적재·볼륨 초기화는 하지 않는다.
5. **실제 연결:** 대표 질문·문의처·범위 거절·요약·DOM을 고정 입력으로 각 필요한 최소 횟수만 확인한다. 원문 판정과 첫 출력·실패 단계·지연을 분리한다. 임베딩 업로드 중 모델 품질 시험을 병렬 실행하지 않는다.
6. **Chrome·관리자 UI:** 지원 도구로 실제 설치 버전·Vercel 후보 배포를 확인하고 공개 상담/F5·패널·낭독·권한·업로드·통계·재발급을 수행한다. 설치 확장 재로드는 지정 시점 한 번으로 묶는다. 도구로 불가능한 청취/기기 조작만 사용자 확인으로 표시한다.
7. **W15 실제 교체:** 관리자 접근이 바뀌므로 별도 확정한 시점에 초기화·발급·새 로그인·구세션 거절·재시작 영속을 확인한다. 사용자에게 전달될 새 비밀번호를 일반 로그/검사 출력에 남기지 않는다.

### 단계 E. 배포와 복구 판정

- **배포 가능:** 후보 SHA의 내부/실제 검증 통과, 미구현·필수 미확인 없음, API 소비자 호환·DB/해시 저장 준비·운영 모델/설정·복구 범위 확인.
- **조건부 보류:** EC2/Chrome/고지/제품 결정/자료/승인 중 필수 항목이 남으면 해당 항목과 이유를 명시한다. W14 비활성 상태의 기존 서비스 배포 가능성과 W14 기능 완료는 별도 판정한다.
- **배포 불가:** 원본 검사 미해결 실패, 개인정보/권한 위반, 데이터 유실, 로그인 잠김, 공개 경로 불통, 새 UI와 API 계약 불일치가 있으면 최종 병합을 막는다.
- Vercel main 자동 배포가 켜져 있으면 **최종 PR 병합 자체가 배포를 유발**한다. 서버 호환 준비 → 후보 프런트/확장 검증 → 사용자 최종 PR 승인 → main 병합/자동 배포 → 변경한 경로만 smoke 확인 순서로 진행한다.
- 복구는 확인된 이전 코드/이미지와 호환 설정으로 제한한다. W08 v3 저장을 v2로 강제 환원하거나 W15 옛 비밀번호로 자동 복귀하지 않는다. W14를 비활성화해도 기존 행을 무단 삭제하지 않는다. 운영 데이터·모델·볼륨을 보존한다.
