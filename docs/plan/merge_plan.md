**W04 동시 처리 작업:** 실제 성능 검증 전에 `BackEnd/core/execution.py`, `core/settings.py`, 요청별 QA/모델 호출·공유 캐시 수명, 관련 gate/기한/취소 검사 및 `docker-compose.yml`의 모델 병렬 설정을 대조한다. 요청별 컨텍스트·프로필·응답·기록이 섞이지 않는지, 4번째 초과 요청·취소·deadline 이후 실행 슬롯 반환이 올바른지 확인한다. 단순 세마포어 값 변경이나 Uvicorn worker 추가만으로 완료하지 않는다. EC2 GPU/메모리 측정 결과에 따라 필요한 설정 변경안을 준비하되 모델 교체·서버 증설·유료 자원 변경을 자동 승인된 것으로 보지 않는다.

**LLM 상주·Docling 필요 시 로드:** 착수 기준선은 최대적재1·병렬1·명시적 keep-alive 없음이었다. 현재 후보 Compose와 EC2는 최대적재2·병렬3·keep-alive -1이며 CPU 임베딩과 기존 Qwen3의 동시 상주를 확인했다. 모델 준비 시간은 현재80초 성능 측정과 구분해 보존한다. Docling 실제 문서 작업 중 로드·종료 후 해제와 작업 뒤 상담은 미검증이며 별도 승인된 문서 시험에서 확인한다. 모델·정밀도·컨텍스트/출력 한도를 바꾸지 않는다.

`BackEnd/documents/analysis.py`는 `analyze_file` 내부에서 Docling을 import하고 converter를 생성하며, `documents/worker.py`는 문서별 자식 프로세스로 처리한다. 따라서 새 상주 Docling 서비스를 만들거나 전체 worker를 껐다 켜는 방식부터 도입하지 않는다. 작업 없음 상태에서 Docling 모델 미로딩, 완료/실패/취소 시 자식 종료·메모리 회수, 기존 모델 디스크 캐시 재사용을 검증하고 확인된 누수만 수정한다. PDF 파이프라인은 현재 CPU 사용이므로 GPU 메모리와 호스트 메모리 결과를 구분한다. Docling 첫 사용의 로드 지연은 관리자 문서 처리 상태로 안내하며 상담 응답 성능과 혼동하지 않는다.

### W12 별도 상담 웹 후속 설계

**이번 산출물은 설계이며 구현·배포는 후속 태스크다.** 기존 관리자 `FrontEnd`와 분리한 반응형 정적 상담 웹을 기준으로 하고, 필요할 때 같은 웹에 PWA 설치 편의를 더한다. 새 앱·패키지·폴더·프로젝트·도메인은 이번에 생성하지 않는다. 후속 작성·검증 담당은 Codex이며 실제 착수 때 별도 태스크·브랜치·폴더와 사용자 공개 범위를 고정한다.

사용 흐름은 공개 HTTPS 접속 → 기기 보관/서버 전송/활성 연락처 수집 고지 → 질문 → 공식 출처·조건/예외·담당 연락처 → 후속 질문 → 현재 상담 요약 → 기기 내 기록 다시 열기/삭제다. 최근30문답, 실제 발화7일 이상 자동 맥락 제외/화면 보존, 선택 프로필 기본 OFF·ON 최종 생성만·OFF 새 경계, 부분 요약 표시는 확장과 같은 의미를 유지한다. 다른 사이트 위 플로팅·DOM 안내·자동 클릭·사용자 계정·기기 간 동기화는 최소 범위에서 제외한다. 추천3개·로컬 낭독/음성 입력은 플랫폼 지원과 명시적인 입력/로컬 음성을 확인한 뒤 제공하며 지원하지 않아도 텍스트 상담을 유지한다.

API는 기존 EC2 HTTPS의 `/api/v1/chat`, `/api/v1/chat/capabilities`, `GET/POST /api/v1/conversation/summary`를 재사용한다. `profile_context`의 동의/프로필 revision, `conversation_context`, 출처/contacts와 오류 DTO를 그대로 소비하며 새 모델·서버 상담 저장·관리자 세션/관리자 API를 복제하지 않는다. 입력·토큰·시간 상한, 요청별 취소·단절·늦은 응답 폐기, 429 busy/rate·504와 사용자의 직접 재시도를 구분한다. UI만 만들고 이 경계를 생략하거나 무한 자동 재시도를 추가하지 않는다.

저장은 웹 origin 전용 IndexedDB 등의 어댑터를 후속 구현한다. `chrome.storage`를 웹에서 쓸 수 있다고 가정하지 않으며 기존 worker와 동등한 직렬 revision·검증·유한 용량·원자 쓰기·실패 시 원본 보존을 제공한다. 확장 기록의 자동 공유/무단 이관은 하지 않는다. 원문 기록·선택 프로필·동의 상태는 기기 내 보관, 요청 시 필요한 범위만 EC2 전송, 사용자 요약 결과는 메모리에만 보관한다. 저장소 삭제·사생활 모드·용량 초과에 따른 유실 가능성을 안내한다. PWA를 더해도 서비스 워커는 정적 앱 셸만 캐시하고 상담 본문·프로필·요약·API 응답을 캐시하지 않는다. 네트워크 없는 새 답변 생성은 제공하지 않는다.

배포는 기존 관리자 AuthProvider/AdminGate/라우트를 보존하고 별도 사용자 웹 빌드·호스트와 기존 EC2 API를 조합한다. 공개 빌드값은 API HTTPS 주소만 사용하며 `.env` 전체·DB 키·관리자 비밀번호를 넣지 않는다. 실제 production 및 필요한 preview origin만 정확한 CORS 목록으로 추가하고 `*`/credentials 우회를 하지 않는다. 새 웹과 확장은 같은 서버의 실행3건·IP 빈도 제한을 공유하며 사용자 웹이 생겨도 서버 용량이 늘지 않는다. 공개 전에 남용·동시3건/각80초 최종 표시와 운영 공개 범위를 재확인한다.

대안 비교는 다음과 같다.

- 반응형 웹: URL 접근으로 설치 부담이 작고 이번 상담 전용 범위에 맞는다. 타사이트 DOM 안내는 제공하지 않는다.
- PWA: 같은 웹/서버 계약에 설치·정적 앱 셸 편의를 더한다. 오프라인 추론이나 기기 간 동기화가 자동으로 생기지 않는다.
- Safari 확장: 기존 WebExtension 일부를 재사용할 수 있어도 앱 패키징·Apple 플랫폼 테스트·App Store Connect 배포 검토가 더 필요하다. 현재 Apple은 Mac/Xcode 없이 ZIP을 패키징하는 경로도 안내하므로 Mac/Xcode를 절대 필수로 단정하지 않는다. [Apple Safari 확장 안내](https://developer.apple.com/safari/extensions/).
- 네이티브 앱: 플랫폼별 UI·저장·권한 수명·배포를 별도 구현해야 하므로 현재 최소 범위에 채택하지 않는다. 데스크톱 Chrome 확장이 모바일 Chrome에 그대로 설치된다고 전제하지 않는다. [Chrome Extensions DevRel의 모바일 지원 답변](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/tCUm3kceybk).

후속 최소 검증은 Android Chrome/iPhone Safari 각1실기기의 회전·가상 키보드·좁은 화면·포커스·출처 열기, 질문/후속·요약·기록 복원/삭제, OFF·ON→OFF·7일 경계, 취소/지연·429·오프라인·저장 실패다. 새 웹과 확장의 동시3건 응답 혼입 없음, 관리자 비인증 차단·미허용 CORS 거절도 확인한다. 마이크/낭독은 해당 플랫폼 지원·명시 입력/로컬 음성을 확인하고 별도로 평가한다. 이 설계 완료를 웹 제작·실기기·모바일 품질 검증 완료로 표시하지 않는다.

## 4. Vercel·EC2 배포 적합성 검증

### 단계 C. EC2 없이 먼저 마칠 검증

1. Docker의 Python 3.12·Node.js 22 환경에서 변경별 집중 검사 후, 결함/누락 정리가 끝난 시점에 원본 전체 내부 검사를 1회 실행한다. 이후는 변경 영향 범위만 재검사한다. Linux 잠금을 Windows에 직접 설치하지 않는다.
2. 실제 `.env`를 읽거나 마운트하지 않는다. backend는 설정 환경 제거·`env_file=None`·모델 offline·네트워크 차단으로 실행한다. DB 테스트는 격리 합성 DB와 운영 DB를 명확히 나눈다.
3. FrontEnd `test:ci`·`build:ci`, TypeScript·정적 리소스·SPA 경로를 확인한다. 운영 `VITE_API_BASE_URL`은 기존 EC2 HTTPS이어야 한다. CI의 `https://example.invalid` 빌드 통과는 운영 주소 확인을 대신하지 않는다.
4. Compose·Dockerfile·Caddy·잠금 의존성·신규 파일의 이미지 포함·worker 연결을 더미 설정으로 검토한다. `docker compose up -d --build`와 기존 운영 profile/override를 유지하며 비밀값이 치환된 전체 설정은 출력하지 않는다.
5. **모델 설정 주의:** 저장소 Compose의 기본 `qwen2.5:1.5b-instruct`와 기존 EC2 운영 모델 `qwen3:30b-a3b-instruct-2507-q4_K_M`은 다르다. 실제 운영 주입값·기존 GPU/runtime·캐시를 확인하기 전 기본 Compose만 실행하지 않는다. 임의 다운로드/교체는 하지 않는다.
6. 배포 순서별 호환을 확인한다. 새 Vercel UI→옛 API, 새 API→기존 확장, 새 확장→API의 지원 기능/오류 처리를 점검한다. W10/W13처럼 새 계약이 필요한 UI는 서버가 준비되기 전에 사용 가능으로 노출하지 않는다.
7. W14는 `REFERRAL_RECORDS_ENABLED=false`에서 migration 없이 기존 상담이 유지되는지 확인한다. 활성화하려면 `0006_contact_referrals.sql`, 기존 department/document 버전, 수집 고지, backend/worker 동일 설정, 삭제 스케줄 준비가 필요하다. 만료 행은 조회 제외하되 물리 삭제는 worker 중단 시 지연될 수 있음을 확인한다.
8. W15는 `ADMIN_CREDENTIALS_FILE` 미설정의 기존 로그인 호환과, 설정한 영속 해시 파일 경로/권한·초기화·복구 절차를 구분한다. 컨테이너 재생성 때 비밀번호가 사라지는 구성을 배포하지 않는다.

**C 완료:** 내부 검사 실패 0건, 모든 skip의 이유/대체 검증 확인, 최종 계약·마이그레이션·환경 변경 목록·복구 절차 준비. 이 단계만으로 운영 배포 안전 판정을 내리지 않는다.

### 단계 D. 사용자가 EC2를 켠 뒤 실제 검증

EC2 기동은 사용자가 한다. 기동 확인 뒤 필요한 시험 시점에 연결한다. **기동 사실만으로 배포·재시작·DB 쓰기·관리자 비밀번호 교체를 승인받았다고 해석하지 않는다.** 실제 실행 전에 대상 SHA·서비스·호출/자료 범위·변경/복구 영향을 제시해 필요한 범위만 확인한다.

1. **읽기 사전 점검:** 실제 EC2 checkout/image SHA, 실행 backend/worker/edge·모델 식별, 기존 GPU·캐시·볼륨, API 주소/TLS, 현재 활성 문서 버전을 확인한다. 키·환경 전체·비밀번호는 출력하지 않는다.
2. **현재 서버 기준선:** 최소 health와 공개/관리자 접근 경계를 확인한다. 공개 게시 문서만 익명 상담 가능, 진단/비공개/test_only는 차단, CORS·세션·rate/gate를 구분한다. 200 또는 container running만으로 통과하지 않는다.
3. **배포 후보 검증:** 최종 병합 전에 fix-merge의 식별된 후보 SHA를 검증할 수 있는 대상과 반영 방식을 정한다. 기존 운영 서버밖에 없으면 필요한 서비스 반영/중단·복구 범위를 먼저 제시한다. main에 먼저 넣고 나중에 검증하는 순서로 바꾸지 않는다.
4. **데이터 작업:** W02는 기존 DB 10개의 대상 문서/제도/버전·게시 상태를 고정하고 대표 1개→나머지 9개 순서로 확인한다. 필요한 추가 업로드/교체만 변경 범위를 확정해 실시하며 수집 자료 전체 투입은 후속이다. W14 DDL/수집 시험은 별도 승인 범위에서 합성 입력으로만 실행한다. 전체 삭제·재적재·볼륨 초기화는 하지 않는다.
5. **실제 연결:** 대표 질문·문의처·범위 거절·요약·DOM을 고정 입력으로 필요한 최소 횟수만 확인한다. 원문 판정과 첫 출력·실패 단계·지연을 분리한다. W04 시험창에 모델 준비 후 동시3건의 각80초 이내 최종 표시·응답 독립성·품질·GPU/메모리를 확인한다. 초기60초와 그 미달 이력은 보존한다. 시작/완료 시각·입력·SHA·자료 버전을 남기며 작은 표본을 전체 지연 보장으로 표현하지 않는다. 임베딩 업로드와 성능 시험은 겹치지 않는다.
6. **Chrome·관리자 UI:** 지원 도구로 실제 설치 버전·Vercel 후보 배포를 확인하고 공개 상담/F5·패널·낭독·권한·업로드·통계·재발급을 수행한다. 설치 확장 재로드는 지정 시점 한 번으로 묶는다. 도구로 불가능한 청취/기기 조작만 사용자 확인으로 표시한다.
7. **W15 실제 교체:** 관리자 접근이 바뀌므로 별도 확정한 시점에 초기화·발급·새 로그인·구세션 거절·재시작 영속을 확인한다. 사용자에게 전달될 새 비밀번호를 일반 로그/검사 출력에 남기지 않는다.

### 단계 E. 배포와 복구 판정

- **배포 가능:** 후보 SHA의 내부/실제 검증 통과, 미구현·필수 미확인 없음, API 소비자 호환·DB/해시 저장 준비·운영 모델/설정·복구 범위 확인.
- **조건부 보류:** EC2/Chrome/고지/제품 결정/자료/승인 중 필수 항목이 남으면 해당 항목과 이유를 명시한다. W14 비활성 상태의 기존 서비스 배포 가능성과 W14 기능 완료는 별도 판정한다.
- **배포 불가:** 원본 검사 미해결 실패, 개인정보/권한 위반, 데이터 유실, 로그인 잠김, 공개 경로 불통, 새 UI와 API 계약 불일치가 있으면 최종 병합을 막는다.
- Vercel main 자동 배포가 켜져 있으면 **최종 PR 병합 자체가 배포를 유발**한다. 서버 호환 준비 → 후보 프런트/확장 검증 → 사용자 최종 PR 승인 → main 병합/자동 배포 → 변경한 경로만 smoke 확인 순서로 진행한다.
- 복구는 확인된 이전 코드/이미지와 호환 설정으로 제한한다. W08 v3 저장을 v2로 강제 환원하거나 W15 옛 비밀번호로 자동 복귀하지 않는다. W14를 비활성화해도 기존 행을 무단 삭제하지 않는다. 운영 데이터·모델·볼륨을 보존한다.
